# Plán: release flow od 2.0.0

Pracovná poznámka k 2.0.0, po vykonaní zmazať. Stav: návrh, nič sa nespúšťa. Zapracovaných je šestnásť kôl review Codex (gpt-5.6-sol, high) a Opus (xhigh) z 2026-09-24 aj prieskum hotových nástrojov. Po 3. kole sa final prestaval na „najprv tag, potom merge“, po 4. kole sa doplnila identita vydaného commitu, obnova a kontrola tagov, po 5. kole identita tagu medzi jobmi, vek tagu, commit vydanej verzie z registry a ručne mergnutý release PR, po 6. kole úzka definícia nevydanej verzie v `main`, obnova bez vytvárania tagov a drafty, po 7. kole poradie obnovy tagu a draftu (8. kolo: GO od oboch), po 9. kole (úplný review) bootstrap a kompatibilita release-tools a bezpečnosť pushov a tagov, po 10. kole (úplný review) prvý commit prázdneho repa, `npm version` bez skriptov, fetch bez tagov a poradie mazania behov, po 11. kole fetch s `--refmap=`, behy pred tagom a prvý commit prázdneho repa ako prvý krok, po 12. a 13. kole cieľ refspecu vetiev, kontrola pred mazaním behov pri zrušení a prunovanie len tagov nástroja; 14. a 15. kolo (úplné review) dali GO od oboch, ich drobnosti sú v rozhodnutiach 41 a 42. Po nich sa podľa podnetu DevOps rozhodlo, že release-tools ostane verejné a na npm sa nepublikuje (rozhodnutie 44); 16. kolo (úplný review po tejto zmene) dalo GO od oboch a jeho drobnosti sú v rozhodnutí 45. **Plán je finálny.** Čo sa z review vedome nezapracovalo, je s dôvodom v rozhodnutí 34.

Dokumentácia má dve časti:
- **Úplná príručka** so všetkými situáciami a kontrolami bude v repe nástroja ako `docs/guide.md`. Kým repo neexistuje, jej návrh je v [`2.0.0-RELEASE-TOOLS-DOCS.md`](2.0.0-RELEASE-TOOLS-DOCS.md).
- **V common-admin** je len krátky výťah [`RELEASING.md`](RELEASING.md): príkazy, pravidlá, jeden príklad na každý prípad a odkaz na úplnú príručku. Po schválení na neho odkáže README.

## Ciele

- Dva príkazy na release, `release:start` a `release:publish`, a tretí, `release:cleanup`, na upratovanie. Príkaz `release:init` jednorazovo pripraví nový projekt. Vetvy, tagy ani GitHub Releases sa nerobia ručne.
- Nástroj je v samostatnom repe `anzusystems/release-tools`:
  - dá sa použiť v ktoromkoľvek projekte,
  - podporuje npm, pnpm aj yarn 4+,
  - funguje aj pre projekty, ktoré na npm nepublikujú, napríklad aplikácie (`publish: "none"`),
  - má vlastné testy vrátane testov na skutočnom GitHube.
- Changelog píše človek, jeden súbor na verziu: `doc/changelog/<verzia>.md`. Nič sa negeneruje.
- Pokryté prípady:
  - release najnovšej línie (patch, minor, major),
  - pre-release (alpha, beta, rc) z release vetvy aj z hocijakej inej vetvy,
  - dev build z hocijakej vetvy, len na GitHube, nie na npm,
  - hotfix staršej verzie z tagu, keď je `main` už ďalej.
- **Každé vydanie spustí push tagu verzie** a každé vydanie sa buildí a kontroluje na presne tom commite, na ktorom je tag. Aj finálna verzia: tag dostane schválená hlava release PR, a až po úspešnom vydaní sa PR mergne do `main`.
- **Nástroj nikdy nepushuje do `main`.** Do `main` sa dostane len merge PR, a pri release PR až po vydaní. `main` je preto vždy len vydaný stav. Na nastaveniach repa (rulesety, schválenia, povinné checks) nezávisí: ak ich projekt má, nástroj sa im prispôsobí, nič neobchádza bez potvrdenia a nič v nich nemení.
- Bezpečnosť:
  - Nič sa nezmení, kým neprejdú všetky kontroly.
  - Každý krok sa dá spustiť znova.
  - `npm publish` beží len v GitHub Actions a spustí ho len push tagu verzie.
  - Priečinok a lokálna vetva sa zmažú až po overenom vydaní a len vtedy, keď v nich nie je nič, čo by sa stratilo. Vetvu na GitHube môže zmazať GitHub pri merge release PR; ten nástroj spraví až po vydaní.

## Úlohy pre DevOps

Žiadny blocker. Nástroj sa na npm nepublikuje (rozhodnutie 44), takže netreba práva v npm organizácii, prvé vydanie tokenom ani trusted publisher pre release-tools. Ostávajú úlohy:
- na npmjs.com zapnúť pri `@anzusystems/common-admin` „Require 2FA and disallow tokens“. Až potom platí, že publikovať sa dá naozaj len z GitHub Actions;
- zlý npm tag po publikovaní sa cez trusted publishing opraviť nedá; opraví ho DevOps ručne (pozri „Akcia“);
- keď niekedy vznikne nový npm balík: token na jeho prvé vydanie a trusted publisher s povoleným priamym `npm publish` (konfigurácie vytvorené po 3. 9. 2026 predvolene povoľujú len staged publish), pozri „Prvé vydanie nového npm balíka“.

## Model

- **`main` = posledný vydaný stav najnovšej línie** (v common-admin platí od 2.0.0). Release PR sa doň mergne až po vydaní, takže `main` nikdy neobsahuje nevydanú verziu.
  - Do `main` sa mergujú len release PR (po vydaní) a zmeny mimo balíka (`.github/`, `doc/`), ktoré idú bežným PR a nič nevydajú.
  - **Release PR sa mergne merge commitom** `release: X.Y.Z`. Commit s tagom tak ostane v histórii `main` a `git log --first-parent main` ukazuje len releasy a zmeny v `doc/` a `.github/`.
- **Dočasné vetvy vytvára len `release:start`, každú vo vlastnom git worktree vedľa repa:**

  | vetva | z čoho | worktree | koniec |
  |---|---|---|---|
  | `release/3.1.0` | `origin/main` | `../<repo>-release-3.1.0` | tag `3.1.0` na schválenej hlave → vydanie → merge do `main` → vetva zmazaná (ostane, ak má commity mimo `main`); alebo zrušenie |
  | `hotfix/2.30.2` | tag `2.30.1` | `../<repo>-hotfix-2.30.2` | tag `2.30.2` → vydanie → PR s changelogom do `main` → vetva zmazaná (ostane, ak má commity za tagom) |

- **Do release a hotfix vetiev sa merguje čokoľvek a akokoľvek.** Na správach commitov nezáleží.
- **Zmena verzie otvoreného releasu nemá vlastný príkaz.** Keď sa z 3.1.0 má stať 4.0.0:
  1. `release:start` → major → `release/4.0.0`,
  2. do nej sa mergne `release/3.1.0` a obsah `3.1.0.md` sa presunie do `4.0.0.md` (súbor `3.1.0.md` sa zmaže),
  3. `release:start` → zrušiť `release/3.1.0`; otvorené PR do nej príkaz ponúkne presmerovať na `release/4.0.0`,
  4. ďalej sa pokračuje s `release/4.0.0` (pre-release alebo final).

  Final potom skontroluje, že vo vetve neostal changelog inej nevydanej verzie. Postup je v príručke nástroja.
- **Tagy nástroja** sú anotované a v popise nesú druh vydania: `release-tools: final` (`hotfix`, `prerelease`, `dev`), pri finale číslo release PR, pri finale a hotfixe s `requireTestedPrerelease` aj zafixovaného kandidáta a `confirmed-by: <login>`, ak používateľ potvrdil bypass alebo ručne mergnutý release PR.
  - **Dátum v tagu** (tagger) zapíše CLI priamo do tag objektu (riadok `tagger` pre `git mktag`, ktorý `GIT_COMMITTER_DATE` nečíta) podľa času servera GitHubu (hlavička `Date` čerstvej odpovede API), nie podľa lokálnych hodín. Akcia podľa neho odmietne starý tag pushnutý znova (pozri „Kroky akcie“).
  - **Lokálne tagy nástroj nečíta ani nemení.** Tag objekt vytvorí CLI bez lokálneho `refs/tags/…` (`git mktag`) a pushne ho ako `<sha>:refs/tags/X`. Všetky pushy CLI sú s `--no-follow-tags`, aby git pri `push.followTags=true` nepribalil lokálne tagy, ktoré na GitHube chýbajú (napríklad zmazané cez `cleanup` alebo zrušenie). Tagy z GitHubu sú v `refs/release-tools/tags/*`.
  - **Každý tag je nový objekt:** popis tagu obsahuje aj náhodné `id: <hex>`, takže tag s rovnakým commitom, popisom a sekundou má vždy iné SHA ako predchádzajúci.
  - **Za tagy nástroja** sa považujú len anotované tagy vo formáte nástroja (`X.Y.Z`, `X.Y.Z-(alpha|beta|rc).N`, dev formát) s popisom `release-tools: …`. Iné tagy (napríklad staré lightweight tagy admin-dam) nástroj nemaže, neopravuje ani nevydáva; pri kontrole, či je verzia obsadená, sa však berie do úvahy každý tag.
  - Stav tagov nástroj vždy zisťuje na GitHube, lokálne tagy nerozhodujú.
- **Bootstrap** (jedna definícia pre CLI aj akciu): trvá, kým posledná vydaná stabilná verzia nemá tag nástroja `release-tools: final` alebo `hotfix`. Počas bootstrapu sa preskočí kontrola verzie v `origin/main:package.json` v `start`, kontrola predka v akcii a detekcia „vydaný, ale nemergnutý release“, a final pripustí verziu rovnú verzii v `origin/main:package.json` (napríklad `1.0.0` z výstupu `init` pri prvom vydaní nového projektu). V common-admin (staré tagy zmazané) aj v admin-dam (tagy bez nástroja, `package.json` s `0.0.1`) tak prvý final prejde.
- **Vydaná verzia** = verzia na npm; pri `publish: "none"` GitHub Release, ktorého tag má formát stabilnej verzie alebo pre-release, bez ohľadu na to, či je tag anotovaný (aj staré releasy admin-dam s lightweight tagmi, takže 2.2.0 je vydaná), a aj draft s takým `tag_name` (pozri nižšie).
  - **Vydaná stabilná verzia** = vydaná verzia bez pre-release časti.
  - **Dev build nie je nikdy vydaná verzia,** ani keď má GitHub Pre-release. Je to samostatná kategória, ktorú maže `cleanup`.
  - **Posledná vydaná verzia línie** sa počíta z vydaných stabilných verzií, nie z tagov.
  - **Stav sa číta čerstvý:** npm z endpointu verzie `/<balík>/<verzia>` (packument má cache 5 min). Zoznam vydaných verzií (napríklad na poslednú vydanú stabilnú) sa zostaví z packumentu aj z tagov na GitHube a nových kandidátov overí endpoint verzie; verzia vydaná pred menej ako 5 min tak nevypadne. Npm tagy sa čítajú vždy z `/-/package/<balík>/dist-tags` (necacheované), nikdy z packumentu. Pri `publish: "none"` sa za vydanú berie aj draft GitHub Release s rovnakým `tag_name`, lebo taký vznikne z publikovaného Release, keď zmizne jeho tag (komunitné zdroje, overí e2e). Nikto iný drafty nevytvára.
  - **Drafty** vracia len zoznam releasov a len s právom push (`GET /releases/tags/{tag}` vracia len publikované). Hľadá ich preto CLI; job `publish` ich vidí len na to, aby nevytvoril druhý Release. Job `build` (`contents: read`) ich nevidí.
  - **Draft vydanej verzie sa zverejní:** keď je verzia vydaná a jej Release je draft, zverejní ho CLI (akcia drafty nemení) (`PATCH` s `draft: false`, `tag_name`, správnym `prerelease` a `make_latest` podľa stavu v tej chvíli), po overení commitu z jeho popisu. Bez `tag_name` by GitHub nastavil `untagged-…`.
    - **Draft sa zverejní len vtedy, keď tag na GitHube existuje** a po dereferencovaní ukazuje na commit z popisu Releasu. Ak tag chýba, najprv ho obnoví (riadok „verzia vydaná, tag chýba“); ak ukazuje na iný commit, platí riadok „vydaná verzia vznikla z iného commitu“. GitHub by inak pri zverejnení vytvoril chýbajúci tag sám z `target_commitish`, teda na hlave `main`, a pri `publish: "none"` by Azure nasadil zlý kód. Ako poistka ide v `PATCH` aj `target_commitish` = tento commit.
    - Poradie pri vydanej verzii je vždy: tag, potom GitHub Release (vytvorenie alebo zverejnenie draftu), potom merge.
- **Commit vydanej verzie** sa zisťuje z registry, nie z tagu: pri npm z provenance verzie (`dist.attestations.url` → SLSA `resolvedDependencies[0].digest.gitCommit`, overené na `vue@3.5.43`; npm ho berie z `GITHUB_SHA` jobu), pri `publish: "none"` z popisu GitHub Release (akcia doň vždy zapíše commit). Akcia pred vytvorením GitHub Release a CLI pred zverejnením draftu a pred merge do `main` overia, že sa rovná commitu tagu.
  - Provenance sa číta až po publikovaní a s opakovaním (odpoveď 404 má cache 60 s).
  - **Verzia bez provenance** (napríklad publikovaná ručne tokenom, kým DevOps tokeny nevypne): CLI po potvrdení berie za commit vydanej verzie commit tagu.
  - **Nezhoda** (verzia vyšla z iného commitu, než na ktorý ukazuje tag): akcia skončí bez Release, CLI nič nemerguje, vypíše oba commity a po potvrdení presunie tag na commit vydanej verzie. Release PR potom pokračuje pravidlom 3 (nový PR z vydaného commitu).
- **Pre-release nič nemerguje a nič nemaže.** Príkaz pushne tag na aktuálny commit vetvy a push tagu spustí publish. GitHub Release je označený ako pre-release. Commit nevzniká, verziu nastaví CI len pri builde.
  - **Výnimka:** rc tesne pred finalom z `release/*` s `requireTestedPrerelease` najprv mergne `origin/main` do vetvy a pushne ju, aby kandidát obsahoval aktuálny `main`. **Hotfix vetva `main` nikdy nemerguje.**
  - **Nepovolí sa**, ak stabilná verzia `X.Y.Z` už je vydaná, ani s verziou nižšou alebo rovnou poslednej vydanej verzii danej línie.
  - Cieľová verzia je daná vetvou: pri `release/X.Y.Z` a `hotfix/X.Y.Z` je to `X.Y.Z`; pri inej vetve predvolene ďalší minor po najnovšej verzii, dá sa zmeniť.
  - Číslo za bodkou je o jedno vyššie ako najvyššie existujúce číslo v tagoch **aj** vo verziách na npm (pri `publish: "none"` v tagoch a GitHub Releases; npm sa vtedy nečíta vôbec, lebo názov balíka tam môže patriť komukoľvek).
  - **Keď pre-release zlyhá** (na npm sa nič nedostalo), tag sa nepresúva: ďalší pokus dostane ďalšie číslo. Tagy nevydaných pre-releasov zmaže `release:cleanup`.
- **Pre-release verzie (alpha, beta, rc) ostávajú navždy:** verzia na npm, git tag aj GitHub pre-release. Nič z toho sa nemaže ani po final verzii, ani po zrušení releasu.
- **Npm tagy sa nikdy neposúvajú späť:**
  - pre-release najnovšej línie → `alpha`, `beta`, `rc`, len ak je vyššia ako verzia, na ktorú tag ukazuje; inak `<id>-X.Y`,
  - pre-release hotfixu staršej línie → `<id>-X.Y`, napríklad `rc-2.30`,
  - hotfix staršej línie → `latest-X.Y`,
  - `latest` sa pri pre-release nikdy nehýbe.
- **Dev build nejde na npm.** Tag spustí build a zbalený balík (`.tgz`) sa priloží ku GitHub Pre-release. Projekt ho inštaluje z URL.
  - Npm totiž zmazanie verzie po 72 hodinách nedovolí, ak má balík za posledný týždeň viac ako 300 stiahnutí (common-admin ich mal 1 599), a ďalšie podmienky (žiadne závislé verejné balíky, jeden vlastník). Číslo zmazanej verzie sa navyše nedá použiť znova.
  - **Verzia:** najbližší tag vo formáte nástroja na GitHube, z ktorého vetva vychádza (dev tagy sa preskočia), a za ním `-dev.<čas UTC>`. Ak je ten tag pre-release, pripojí sa `.dev.<čas>`. Ak vetva žiadny taký tag nemá, základom je verzia z `package.json` bez pre-release časti. Tagy z GitHubu nástroj stiahne do vlastného menného priestoru (`refs/release-tools/tags/*`).
  - **Príklady:** `3.0.0-dev.20260923143000`, `3.1.0-beta.2.dev.20260923143000`.
  - **Vlastný názov nahradí čas:** `3.0.0-dev.new-filter`. Musí začínať písmenom, povolené sú písmená, číslice a pomlčka, celá verzia sa overí podľa semveru. Názov je obsadený, ak existuje tag alebo GitHub Release.
  - **Dev tag sa nikdy nepresúva.** Keď dev build zlyhá, ďalší pokus dostane nový čas alebo iný názov. Dev build ostáva, kým ho nezmaže `release:cleanup`.
  - Pri `publish: "none"` je dev build len tag a GitHub Pre-release, bez `.tgz`.
- **Zdroj pravdy o verzii:**
  - Pri release a hotfix vetvách je to názov vetvy.
  - `package.json` sa mení až vo final commite. Final commit nastaví v `package.json` vydávanú verziu; po merge ju má `main`. Platí to aj v aplikáciách: v admin-dam je dnes `0.0.1`, potom tam bude napríklad `3.0.0`.
  - Pri pre-release a dev builde sa verzia v `package.json` otagovaného commitu líši od verzie tagu. Je to zámer, aby nepotrebovali commit.
- **Nevydaná verzia v `main`** = verzia V z `origin/main:package.json` nie je vydaná **a zároveň** je do `main` mergnutý release PR z vetvy `release/V`. Vznikne len vtedy, keď niekto release PR mergne ručne skôr, ako verzia vyšla.
  - Samotná nevydaná verzia v `package.json` tento stav nie je. Po bootstrap PR má `main` v common-admin `1.47.0-beta.dev-…` a admin-dam `0.0.1`, ani jedna nie je vydaná a prvý final musí prejsť bežne.
  - `start` vtedy nový release z `main` nezačne (hotfix staršej línie áno) a odkáže na `release:publish`; `publish` ju po potvrdení otaguje a vydá, kontrola verzie pri tom vyžaduje rovnosť s `main` namiesto vyššej verzie (pozri „Release PR mergnutý alebo zatvorený mimo nástroja“). Zrušenie sa v tomto stave odmietne, lebo verzia už je v `main`.
- **Vydaný, ale nemergnutý release:** stabilná verzia najnovšej línie je vydaná, ale jej commit s tagom ešte nie je predkom `main` (napríklad release PR čaká na schválenie). Kým trvá, nový release z `main` ani ďalší final nepustia; hotfix a zrušenie iných releasov fungujú. `publish` ponúkne dokončiť merge.
- **Changelog súbor vytvorí `release:start` zo šablóny.** Existujúci súbor nikdy neprepíše. Hlavička `<verzia> — unreleased` sa pri final publish zmení na dátum.
- **Changelog hotfixu staršej verzie** (`2.30.2.md`) sa po vydaní dostane do `main` samostatným PR `docs: changelog 2.30.2` s týmto súborom a riadkom v indexe.
- **Index `CHANGELOG.md` dopĺňa nástroj** (v common-admin aj v admin-dam, pole `changelogIndex`):
  - riadok `- [2.3.0](doc/changelog/2.3.0.md) — 2026-09-24` pridá final commit; index pritom zostaví znova zo súborov v `doc/changelog/`, ktoré majú v hlavičke dátum, takže riadok verzie, ktorá nikdy nevyšla (napríklad po zmene verzie otvoreného releasu), v ňom neostane,
  - dátum je dátum final commitu; pri opakovaní sa nemení, ani keď schválenie trvá dni,
  - pri hotfixe staršej verzie ho pridá PR `docs: changelog …`,
  - riadky sú zoradené podľa verzie zostupne, takže `2.30.2` sa zaradí medzi 2.x,
  - konflikt v indexe nástroj vyrieši tak, že riadky zostaví znova zo súborov v `doc/changelog/`,
  - nástroj prepisuje len súvislý blok riadkov `- [X](…) — dátum`; ostatný text súboru (úvod, odkaz na staršie poznámky) nechá. Keď blok ešte chýba, vloží ho za prvý odsek. V common-admin sa pri zavedení odstráni riadok „planned“, ktorý má iný formát.

## Nástroj `anzusystems/release-tools`

Verejné repo s dvoma časťami:

| časť | čo robí | ako ju projekt použije |
|---|---|---|
| CLI | príkazy `init`, `start`, `publish`, `cleanup` na počítači vývojára | alias v `package.json` projektu, spúšťanie podľa časti „Distribúcia nástroja“ |
| composite action `publish/` | validácia, kontroly, build, balenie, npm publish, GitHub Release v GitHub Actions | stub workflow v projekte s krokom `uses: anzusystems/release-tools/publish@main` |

**Kód:**
- čistý JavaScript (ESM) s typmi v JSDoc a `// @ts-check`,
- **bez runtime závislostí**, len vstavané moduly Node; vývojové závislosti (napríklad `typescript` na `tsc --noEmit`) sú povolené,
- Node 22.14+ (trusted publishing vyžaduje Node ≥ 22.14 a npm ≥ 11.5.1),
- lokálne vyžaduje git ≥ 2.38,
- nie je čo buildiť, `dist` sa necommituje,
- CI repa spúšťa `tsc --noEmit`, unit a integračné testy.

**Distribúcia nástroja** (jedna verzia pre všetky projekty = `main` nástroja):

| fáza | CLI | akcia |
|---|---|---|
| vývoj a testy | lokálny klon: `node ~/projects/anzusystems/release-tools/bin/release.mjs <príkaz>` | z testovanej vetvy: `uses: anzusystems/release-tools/publish@<vetva>` |
| používanie | `npx -y --allow-git=all github:anzusystems/release-tools#main <príkaz>` | `@main` (= vydaný stav) |

- **Repo je verejné a na npm sa nepublikuje** (rozhodnutie 44). Súkromné repo by nešlo: akciu zo súkromného repa GitHub dovolí použiť len zo súkromných rep, a common-admin aj admin-dam sú verejné; obchádzka cez token v každom projekte by pridala údržbu tokenu a jedno miesto, ktoré zastaví všetky vydania. Nástroj nemá žiadne tajné údaje.

- **Nástroj sa vydáva vlastnými príkazmi** (`release:start`, `release:publish`) ako každý iný projekt, s `publish: "none"`: verzia nástroja je tag a GitHub Release. `main` nástroja preto obsahuje vydaný stav a CLI (`github:…#main`) aj akcia (`@main`) sa berú z toho istého `main`. Je to zároveň reálny test cesty `publish: "none"`.
- **Núdzová výnimka:** chyba v akcii, ktorá blokuje vydávanie, zablokuje aj vydanie opravy nástroja, lebo ten sa vydáva akciou `@main`. Oprava vtedy ide priamo do `main` nástroja bežným PR a vydá sa hneď potom.
- **Nové vydanie nástroja platí hneď pre všetky projekty,** preto sa pred každým vydaním spúšťajú všetky testy vrátane e2e (e2e lokálne, pozri „Testy nástroja“).
- **Formát artefaktu** medzi jobmi `build` a `publish` je verzovaná zmluva. Opakovaný job `publish` môže bežať s novšou logikou z `main` nad artefaktom zo staršieho behu.
- **Prvotný bootstrap `main` nástroja:** repo je dnes úplne prázdne (žiadny commit ani `main`) a `release:start` aj `publish@main` potrebujú `main`. PR do neexistujúcej vetvy sa otvoriť nedá, preto:
  1. jeden commit priamo do `main` (README a LICENSE, Apache-2.0 ako common-admin a admin-dam), jednorazová ručná výnimka z „nikto nepushuje do `main`“. Je to úplne prvý krok, pred pushom akejkoľvek inej vetvy, lebo prvá pushnutá vetva prázdneho repa sa stane predvolenou;
  2. bootstrap PR s prvou implementáciou (vrátane `publish/action.yml`), ktorý je zároveň výstupom `init` nad release-tools: stub, `release.config.json`, šablóna changelogu a index. Je to výnimka z „`main` = vydaný stav“, ktorá trvá do prvého vydania; dovtedy idú do `main` cez PR aj ďalšie zmeny nástroja;
  3. prvé vydanie: `release:start` → prvá verzia `1.0.0` (bootstrap podľa Modelu) a `release:publish`, spúšťané z lokálneho klonu (`node bin/release.mjs`). Akcia `@main` je vtedy tá istá ako v tagu. Na nikoho sa nečaká, npm sa nepoužíva.
  - `init` aj `start` v repe bez `main` skončia so správou, že treba najprv prvý commit.
- **Kompatibilita CLI a akcie:** CLI aj akcia sa berú z `main` nástroja a po merge release PR nástroja sa zmenia naraz. Rozídu sa, keď príkaz CLI spustený so staršou verziou beží dlho (napríklad dni čaká na schválenie): medzitým môže vyjsť aj viac verzií nástroja a staré CLI potom číta aj to, čo zapíše nová akcia (text Release s commitom) alebo novšie CLI kolegu. Pravidlá:
  - akcia prijme výstup každej vydanej verzie CLI, nielen predchádzajúcej;
  - popisy tagov, text GitHub Release a schéma konfigurácie ostávajú v repách navždy: formáty sa len rozširujú, čitatelia neznáme riadky a kľúče ignorujú a čítajú aj všetky staré formáty (unit testy majú vzorky všetkých starých formátov);
  - zmena, ktorú staršia verzia nevie ignorovať, ide v dvoch vydaniach: najprv ju nástroj vie čítať, až v ďalšom ju začne zapisovať;
  - artefakt medzi jobmi `build` a `publish` má verziu schémy a akcia číta všetky schémy, ktoré sa ešte dajú zopakovať (30 dní). Pri nepodporovanej schéme job skončí „neplatný beh“ a stabilný tag sa vytvorí znova s celým novým buildom, neopakuje sa ten istý job;
  - CLI pri štarte načíta všetky svoje moduly aj dátové súbory (schéma, šablóny) a neskôr nič z vlastného balíka nečíta: npx drží balík v priečinku podľa špecifikácie, nie podľa verzie, a iné spustenie ho počas čakania prepíše novou verziou (overené pokusom);
  - vydania nástroja po 1.0.0 sa spúšťajú cez aliasy (`github:…#main`), nie z release worktree, aby CLI nebolo novšie ako akcia;
  - testy: CLI N−2 proti akcii N, `build` N−2 proti `publish` N, CLI N−1 dokončí merge nad Release od akcie N, výmena priečinka balíka počas čakania.

- **Výstupy akcie:** `version`, `tag`, `prerelease`, `latest` (true = verzia je GitHub Latest), `published` (true = vydanie v tomto behu prebehlo alebo už bolo hotové) a `released-now` (true, keď vydanie prebehlo v tomto behu, v ktoromkoľvek jeho pokuse: akcia zapíše `run_id` do popisu GitHub Release rovnako ako commit, takže po páde runnera a „Re-run failed jobs“ je `released-now` stále true). Nasadenie sa dá pripojiť ako ďalší job v tom istom release workflowe (`needs: publish`) s podmienkou `released-now == 'true' && latest == 'true'`, aby sa nenasadil hotfix staršej línie. Opakovanie behu („Re-run failed jobs“) však použije výstupy jobu `publish` z pôvodného pokusu, takže podmienka opakovaný starý beh nezastaví: nasadenie musí zniesť opakovanie a tesne pred nasadením overiť, že `tag` je stále GitHub Latest (`GET /repos/{o}/{r}/releases/latest`).
  - GitHub Release, ktorý vytvorí akcia cez `GITHUB_TOKEN`, nespustí iný workflow v GitHub Actions.
  - Externé webhooky, napríklad Azure v admin-dam, ho podľa dokumentácie dostanú normálne. Overí to prvý release admin-dam.
- **Tag pushne CLI ešte pred kontrolami v CI.** Ak Azure reaguje na push tagu, zbuildí aj verziu, ktorú akcia potom odmietne. Bezpečnejšie je, keď Azure reaguje na udalosť GitHub Release (published), prípadne keď nasadenie spúšťa job cez `needs: publish`.

**Prvé vydanie nového npm balíka:**
- Trusted publisher sa na npmjs.com dá nastaviť len pre balík, ktorý už existuje. Dnes žiadny nový npm balík v pláne nie je (release-tools sa na npm nepublikuje), preto to nástroj zatiaľ nerieši (rozhodnutie 45).
- Keď nový balík vznikne, pridá sa do akcie voliteľný vstup s krátkodobým tokenom na jeden beh, zapísaný len do dočasnej používateľskej konfigurácie npm v jobe `publish`; staré stuby to nerozbije. Z počítača sa nepublikuje ani prvá verzia.

**Čo nástroj potrebuje od repa** (nič iné nemení ani neobchádza):
- povolený merge commit do `main` (release PR aj PR s changelogom hotfixu sa mergujú merge commitom). `init`, `start` a znova `publish` pred stabilným tagom skontrolujú všetky tri vrstvy:
  - nastavenie repa `allow_merge_commit` (GraphQL `mergeCommitAllowed`),
  - rulesety pre `main` (`GET /repos/{o}/{r}/rules/branches/main`: `required_linear_history`, `pull_request.allowed_merge_methods`),
  - klasickú ochranu vetvy, ak existuje: `requiresLinearHistory` z GraphQL `branchProtectionRule` (vidí ho admin), inak z `refUpdateRule` (dostupné aj bez práv admina; vracia hodnoty pre prihláseného používateľa, adminovi ich zmierňuje). V repe len s rulesetmi je `refUpdateRule` null,
  - merge queue na `main` nástroj nepodporuje; ak ju vyžaduje ruleset (pravidlo `merge_queue`) alebo klasická ochrana (GraphQL `repository.mergeQueue(branch: "main")`), príkaz skončí,
- existujúci environment z `npmEnvironment` a trusted publisher na npmjs.com (len pri `publish: "npm"`),
- **auto-merge nepoužíva,**
- **povinné schválenie a iné podmienky merge** nástroj rešpektuje: tag finalu vytvorí, až keď je release PR mergovateľný (`mergeStateStatus` `CLEAN`, `HAS_HOOKS` alebo `UNSTABLE`; `UNKNOWN` zisťuje znova). Keď chýba len schválenie a používateľ smie pravidlá obísť, ponúkne bypass a spustí ho až po potvrdení.
  - **Smie ich obísť,** keď pri klasickej ochrane vetvy (ak existuje) platí GraphQL `viewerCanMergeAsAdmin` a pri každom rulesete pre `main` je `current_user_can_bypass` `always`, `pull_requests_only` alebo `exempt`. ID rulesetov dá `GET /rules/branches/main`, pole `current_user_can_bypass` až detail `GET /rulesets/{id}`. Samotné `viewerCanMergeAsAdmin` rulesety nepokrýva (overené v 5. kole: v common-admin by bez rulesetov bypass nikdy neponúklo).
  - `BLOCKED` pri `reviewDecision: APPROVED` (napríklad „extra approval for unattributed changes“) vypíše ako blokáciu pravidlami repa,
- `gh` prihlásený so scope `repo` a `workflow` (`workflow` treba, keď merge alebo push mení `.github/workflows/`),
- git e-mail, ktorý GitHub pozná (commity nástroja podpisuje používateľ). Rulesety oboch rep majú „extra approval for unattributed changes“, takže commity s nepriradeným e-mailom by si vyžiadali ďalšie schválenie; `start` na to upozorní.

## Otestovaný pre-release pred stabilnou verziou

**`requireTestedPrerelease`** (v common-admin zapnuté; platí pre final aj pre hotfix):
- Stabilná verzia `X.Y.Z` sa vydá, len keď sa jej obsah zhoduje s **kandidátom**: najvyšším (podľa semveru) pre-release `X.Y.Z-(alpha|beta|rc).N`, ktorý je vydaný.
- **Kandidáta zafixuje CLI** v popise tagu stabilnej verzie (`release-tools: final; candidate: 3.1.0-rc.2`). CI porovnáva presne s ním, aj keby medzitým vyšiel iný pre-release. Akcia číta `requireTestedPrerelease` z `origin/main`; stabilný tag bez kandidáta pri zapnutej voľbe odmietne.
- **Čo sa porovnáva (v CI):** všetky súbory oboch tarballov (cesta aj hash) okrem `CHANGELOG.md` a súborov v `changelogDir` (final commit mení hlavičku changelogu, npm ich pribalí, keď balík nemá `files`). `npm-shrinkwrap.json` sa porovná bez `version` a bez `packages[""].version`. `package.json` sa porovná bez poľa `version` a bez závislosti s názvom samotného balíka (yarn prepíše odkaz balíka na seba cez `workspace:*` na aktuálnu verziu, overené pokusom). Pri `publish: "none"` sa neporovnáva nič.
- **Keď porovnanie v CI zlyhá,** nič sa nevydá a nič sa nemergne. Vydá sa nový rc a tag finalu sa presunie podľa pravidla „Presun tagu“.
- **Podmienka:** build musí byť deterministický, teda rovnaký kód musí dať rovnaké súbory. Pri common-admin to potvrdil vlastník plánu chunkovania; npm aj yarn dávajú pri rovnakom vstupe rovnaký `.tgz` (overené pokusom).

## `release:init`

Jednorazovo v novom projekte:
1. Zistí, čo sa dá: názov balíka, repo, správcu balíkov, verziu Node (`.nvmrc` alebo `engines`), či projekt publikuje na npm, či má `repository.url`, či repo povoľuje merge commit. Na ostatné sa spýta.
2. **Najprv skontroluje všetky cieľové súbory:** súbor s presne tým obsahom, ktorý by zapísal, je hotový krok; súbor s iným obsahom je konflikt, ktorý treba potvrdiť alebo odmietnuť. Až potom zapisuje, každý súbor naraz (zápis do dočasného súboru a premenovanie).
3. Zapíše:
   - stub release workflow (v novom projekte `.github/workflows/release.yml`, v common-admin existujúci `release-package.yml`) v správnom variante pre `publish`,
   - `release.config.json`,
   - aliasy `release:start`, `release:publish`, `release:cleanup` v `package.json`,
   - šablónu changelogu a index `CHANGELOG.md`, ak chýbajú.
4. Opakované spustenie po prerušení dokončí len chýbajúce súbory.
5. Na konci vypíše, čo treba spraviť ručne: dostať zmeny do `main` bežným PR, nastaviť environment a trusted publisher, prípadne prvé vydanie nového balíka.

## `release:start`

**Menu:**
- nový release z `main`: patch, minor, major a vlastná verzia;
- hotfix staršej verzie: posledná vydaná verzia každej staršej línie, ktorej tag obsahuje stub nástroja, plus iná verzia;
- otvorené releasy (podľa vetiev na GitHube **aj** lokálnych worktree a vetiev): zrušiť;
- zvyšky vydaných releasov (pozri krok 9 finalu a krok 6 hotfixu), vždy s výpisom commitov navyše:
  - release vetva s commitmi mimo `main`: mergnúť do nového releasu, ktorý sa práve vytvára (zvyšok sa potom zmaže, keď je jeho hlava predkom novej release vetvy a nie sú v ňom necommitnuté zmeny ani nepushnuté commity), alebo zmazať po výslovnom potvrdení,
  - hotfix vetva s commitmi za svojím tagom (`<tag>..hlava`): mergnúť do nového hotfixu tej istej línie, alebo zmazať po výslovnom potvrdení. Do releasu z `main` sa neponúka, priniesla by doň starú líniu.

**Kontroly** (pred akoukoľvek zmenou):
- `gh` je prihlásený so scope `repo` a `workflow` a `origin` je repo z konfigurácie;
- `git fetch --no-tags --refmap=` z `origin` prebehol dvakrát: vetvy s refspecom `+refs/heads/*:refs/remotes/origin/*` a `--no-prune` (s prázdnym `--refmap=` by refspec bez cieľa neaktualizoval `origin/main`, overené; `--prune` by zmazal aj iné refy používateľa v `refs/remotes/origin/*`, napríklad z vlastného refspecu pre PR), a tagy s refspecom `+refs/tags/*:refs/release-tools/tags/*` a `--prune`, pri obnove presunu tagu `--no-prune` (nastavenie `fetch.prune=true` by inak prunovalo aj bez prepínača, overené). Či vetva na GitHube existuje, nástroj zisťuje z GitHubu, nie z `origin/*`. Obyčajný `git fetch` by k stiahnutým commitom automaticky vytvoril lokálne tagy a bez prázdneho `--refmap=` by git použil aj `remote.origin.fetch` používateľa, ktorý môže obsahovať `+refs/tags/*:refs/tags/*` (oboje overené). Lokálne tagy nástroj nevytvára, nemaže ani nepushuje; rovnako fetchuje aj `publish`;
- repo má `main`; v prázdnom repe príkaz skončí so správou, že treba najprv prvý commit;
- pri novom releasi z `main`: nie je **vydaný, ale nemergnutý release** ani **nevydaná verzia v `main`** (pozri Model). Ak je, príkaz skončí a povie, že ho treba dokončiť cez `release:publish`;
- repo povoľuje merge commit do `main` a nevyžaduje merge queue (pozri „Čo nástroj potrebuje od repa“);
- **bootstrap** (pozri Model): príkaz nekontroluje verziu v `package.json` a ponúkne verziu, ktorú zadáš, alebo nasledujúcu po najvyššej vydanej verzii;
- inak: verzia v `origin/main:package.json` sa rovná poslednej vydanej verzii najnovšej línie;
- verzia má presne tvar `X.Y.Z` (bez pre-release časti a bez build metadát `+…`, inak by ju akcia pri finale odmietla) a je vyššia ako posledná vydaná stabilná verzia, z ktorej sa vychádza;
- verzia nie je vydaná, nemá tag ani vetvu na origine a neexistuje cudzí priečinok s rovnakým názvom;
- pri hotfixe:
  - základ je posledná vydaná verzia svojej línie a nie je v najnovšej línii (patch najnovšej línie je bežný release z `main`),
  - commit jej tagu obsahuje stub nástroja,
  - verzia je presne nasledujúci patch.

**Kroky:**
1. `git worktree add --no-track -b <vetva> <priečinok> <origin/main | refs/release-tools/tags/<tag>>` (lokálny tag sa nepoužije); ak lokálna vetva s týmto názvom už existuje a patrí tomuto releasu, `git worktree add <priečinok> <vetva>`.
2. Changelog zo šablóny, ak súbor neexistuje, a potom commit (`--no-verify`, aby commit hooky projektu neodmietli správu).
3. `git push --no-follow-tags -u origin refs/heads/<vetva>` (len táto vetva, bez tagov).
4. Skopíruje súbory z `worktree.copy`.
5. Inštalácia podľa správcu balíkov alebo `worktree.install`, potom vypíše cestu k priečinku.

**Opakovanie:** `start` rozpozná svoj čiastočný stav (worktree alebo lokálna vetva s očakávaným názvom existujú, vetva na origine chýba alebo má rovnaký commit) a pokračuje od prvého nedokončeného kroku. Inštalácia sa dá spustiť opakovane.

**Zrušenie** (release aj hotfix):
1. Ak má worktree necommitnuté zmeny alebo vetva nepushnuté commity, vypíše ich a skončí, kým ich používateľ nevyrieši alebo výslovne nepotvrdí, že ich zahodí.
2. **Stav, skôr než sa čokoľvek zmení:** ak je verzia vydaná (aj vydaná, ale nemergnutá) alebo ide o **nevydanú verziu v `main`**, zrušenie odmietne a ponúkne dokončenie cez `release:publish`.
3. Vypíše ostatné otvorené PR, ktorých base je táto vetva, a ponúkne ich presmerovať na inú otvorenú release vetvu alebo zatvoriť. Musí to byť pred zmazaním vetvy, lebo GitHub PR do zmazanej vetvy sám zatvorí. Potom zatvorí release PR a pri hotfixe zmaže vetvu `hotfix/X.Y.Z` na origine (necommitnuté a nepushnuté zmeny overil krok 1). Znovu pushnutý tag tým stratí platnosť (akcia vyžaduje otvorený alebo mergnutý release PR, pri hotfixe existujúcu hotfix vetvu).
4. Tesne pred tým znova overí obe podmienky kroku 2: verzia nie je vydaná a release PR nie je mergnutý (počas interaktívneho kroku 3 mohol beh vydať verziu alebo niekto PR mergnúť; vtedy zrušenie odmietne ako v kroku 2). Potom zmaže dokončené behy stabilného tagu tejto verzie (`DELETE /repos/{o}/{r}/actions/runs/{id}`), aj keď tag už neexistuje (opakované zrušenie po páde), aby ich nikto nezopakoval: „Re-run failed jobs“ by prešiel kontrolou tag objektu, keby niekto z klonu pushol ten istý objekt znova. Potom, ak existuje nevydaný stabilný tag tejto verzie, ho zmaže dvojfázovo podľa „Presun tagu“, bez vytvorenia nového, a zmaže aj behy, ktoré medzitým dobehli. Ak verzia medzitým vyšla, tag obnoví a zrušenie skončí; release sa dokončí cez `release:publish`, pri release podľa pravidla 3 (nový PR z vydaného commitu), pri hotfixe krokmi 5–6 hotfixu.
5. Zmaže worktree a lokálnu vetvu, potom vetvu na origine, ak ešte existuje. Každý krok len vtedy, ak ešte existuje, takže sa dá zopakovať. Prerušené zrušenie dokončí opakovaný `start` → zrušiť.
6. Pre-releasy, dev buildy a ich tagy nechá (tagy nevydaných pre-releasov zmaže `cleanup`).

## `release:publish`

**Menu podľa vetvy:**

| kde | ponuka |
|---|---|
| `release/*` | final, beta, rc, alpha, dev |
| `hotfix/*` | final, rc, beta, alpha, dev |
| iná vetva | dev build tejto vetvy, pre-release (alpha, beta, rc; cieľ = ďalší minor, dá sa zmeniť na inú verziu presne v tvare `X.Y.Z`) a výber otvoreného releasu |
| hocikde, ak existuje | vydaný, ale nemergnutý release; nevydaná verzia v `main`; nedokončené vydanie: stabilný tag otvoreného releasu bez vydanej verzie, tag s čakajúcim alebo bežiacim behom, vydaná verzia bez GitHub Release alebo s draftom, nedokončený presun tagu (zlyhané pre-releasy a dev buildy sem nepatria, tie uprace `cleanup`) |

Mimo release priečinka ponúkne otvorené releasy a pre vybraný pracuje v jeho priečinku; ak neexistuje, vytvorí ho.

**Kontroly** (pred akoukoľvek zmenou):
- Vo worktree nie sú necommitnuté zmeny ani rozpracovaný merge (`MERGE_HEAD`), v zmenených súboroch nie sú konfliktné značky. Nepushnuté commity príkaz pushne (`--no-follow-tags`), **nikdy však `main`:** ak je lokálny `main` pred `origin/main`, príkaz skončí; pre-release a dev build z `main` sa robia len z commitu, ktorý už na origine je. Nové commity z originu stiahne cez fast-forward (`git merge --ff-only`, nie `git pull`), a ak vetvy divergujú, skončí.
- Changelog existuje a obsahuje aspoň jeden riadok, ktorý nie je nadpis, podčiarknutie nadpisu (`===`) ani prázdny. Pri final je to podmienka, pri pre-release len upozornenie, pri dev builde sa nekontroluje. Pre-release bez changelogu dostane ako popis GitHub Release vetvu, commit a poznámku „no changelog yet“.
- **Nový pokus:** verzia ešte nie je vydaná. (Pri pokračovaní už začatého vydania sa vydaná verzia naopak očakáva, pozri „Stav a opakovanie“.)
- Commit, ktorý dostane tag, obsahuje stub nástroja. Na vetve, ktorá ho nemá, lebo je staršia ako zavedenie nástroja, príkaz skončí so správou, že treba mergnúť `main`.
- Správa commitu, ktorý dostane tag, neobsahuje značku, ktorá by beh preskočila: `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]` ani trailer `skip-checks: true` alebo `skip-checks:true`.
- **Final z `release/*` navyše:**
  - nie je iný vydaný, ale nemergnutý release;
  - verzia vetvy je vyššia ako posledná vydaná stabilná verzia a ako verzia v `origin/main:package.json`; v stave **nevydaná verzia v `main`** sa verzii v `main` naopak rovná. Ak nie (napríklad 3.1.0 vyšla skôr ako 3.0.1), príkaz skončí a navrhne nový release s vyššou verziou;
  - repo povoľuje merge commit do `main` (overí znova pred tagom);
  - žiadny otvorený PR okrem release PR nemá ako base túto vetvu. Ak nejaký má, príkaz ich vypíše a ponúkne presmerovanie na inú otvorenú release vetvu alebo zatvorenie. Kontrolu zopakuje pred merge v kroku 7 aj pred zmazaním vetvy v kroku 9: PR otvorený do vetvy po tagu by GitHub pri zmazaní vetvy zatvoril alebo presmeroval na `main`, a jeho merge by dal do `main` nevydaný kód;
  - vo vetve nie je changelog inej nevydanej verzie (napríklad `3.1.0.md` v `release/4.0.0`);
  - pri `requireTestedPrerelease`: existuje vydaný kandidát; zhodu obsahu rozhodne CI;
  - žiadny stabilný tag najnovšej línie, ani tag tejto verzie, nemá čakajúci alebo bežiaci beh (okrem behov zo zmazania refu); po ich dobehnutí sa stav vydania overí znova;
  - neexistuje nevydaný stabilný tag inej verzie najnovšej línie (napríklad 3.0.1, ktorého job `publish` zlyhal). Príkaz ponúkne tri možnosti: ten release dokončiť, zrušiť (rovnaký postup ako `start` → zrušiť, zmaže aj jeho behy), alebo len **stiahnuť jeho tag**: dvojfázovo zmaže nevydaný stabilný tag a jeho dokončené behy ako krok 4 zrušenia, pričom vetva, worktree aj PR ostanú a jeho ďalší final vytvorí tag nanovo (riadok „tag chýba, PR mergovateľný“). Tretia možnosť odblokuje urgentný patch, keď kontroly väčšieho releasu zlyhali; tag, ktorý už nemá vetvu, zmaže `cleanup`. Bez tejto kontroly by zopakovaný beh druhého releasu mohol vyjsť až po tomto finale. Dva finaly naraz by inak mohli vyjsť v zlom poradí (3.1.0 bez opravy z 3.0.1) a starý beh presúvaného tagu by mohol vydať iný commit, keď iný počítač tag vytvorí znova.
- **Final z `hotfix/*` navyše:** pri `requireTestedPrerelease` existuje vydaný kandidát; tag tejto verzie nemá čakajúci ani bežiaci beh (okrem behov zo zmazania refu), po ich dobehnutí sa stav vydania overí znova.
- **Final aj pre-release z `hotfix/*`:** rovnaká kontrola predkov ako v akcii: tag základnej verzie je predkom commitu a žiadny tag vydanej stabilnej verzie vyššej línie nie je predkom. Inak (napríklad niekto omylom mergol `main` do hotfixu) príkaz skončí ešte pred tagom a navrhne hotfix zrušiť a začať znova; rc s kódom novej línie by inak vyšiel na npm natrvalo.

**Final z `release/*`:**
1. Lokálne vo worktree mergne `origin/main`.
   - V `package.json`, `package-lock.json` a `npm-shrinkwrap.json` vyrieši automaticky len konfliktné bloky, ktoré sa líšia výhradne vo verzii (`version`, v lockfile aj `packages[""].version`), a to na verziu vetvy. Ostatné zmeny v týchto súboroch (napríklad závislosti z oboch strán) zlúči git sám a každý iný konfliktný blok je „iný konflikt“. Nikdy sa neberie celý súbor z jednej strany, lebo by sa potichu stratili zmeny závislostí (overené pokusom). Konflikt v indexe `CHANGELOG.md` vyrieši zostavením indexu znova. Rovnaké automatické riešenie platí aj pri overení mergov podľa `git merge-tree` v kroku 7.
   - Pri inom konflikte nechá merge rozpracovaný a skončí. Konflikt vyriešiš v IDE, commitneš a spustíš príkaz znova.
2. Final commit `release: 3.1.0` (`--no-verify`) zmení verziu v `package.json` (pri npm cez `npm version 3.1.0 --no-git-tag-version --ignore-scripts --allow-same-version`, aby sa zmenil aj `package-lock.json` a `npm-shrinkwrap.json`, nespustili sa skripty projektu `preversion`, `version` a `postversion` a opakovanie s rovnakou verziou nezlyhalo), hlavičku changelogu na dátum a doplní riadok do indexu `CHANGELOG.md`.
3. Push a potom PR `release: 3.1.0` do `main`. Ako popis PR použije changelog.
4. **Čaká, kým je PR mergovateľný** podľa pravidiel repa (`gh pr view --json mergeStateStatus,reviewDecision,headRefOid`):
   - `CLEAN`, `HAS_HOOKS` alebo `UNSTABLE`: pokračuje,
   - chýba schválenie: vypíše odkaz na PR a čaká. Ak chýba už len schválenie a používateľ smie pravidlá obísť (pozri „Čo nástroj potrebuje od repa“), ponúkne „Vydať a mergnúť bez schválenia (bypass)?“; po potvrdení pokračuje a potvrdenie zapíše do tagu (`confirmed-by`),
   - `BEHIND` alebo konflikt (`DIRTY`): zopakuje krok 1 a 2 (bez nového final commitu, ak už existuje), pushne a čaká ďalej,
   - ak sa medzitým pohol `main` alebo hlava PR, zopakuje všetky kontroly finalu.
5. **Tag:** zopakuje kontroly finalu na aktuálnej hlave PR `H`, pri `requireTestedPrerelease` určí kandidáta a vytvorí anotovaný tag `3.1.0` na `H` s popisom `release-tools: final; pr: <n>; candidate: <verzia>` (prípadne `; confirmed-by: <login>`) a s dátumom zo servera GitHubu. Pushne len tento tag (`git push --no-follow-tags origin <sha>:refs/tags/3.1.0`). Push tagu spustí release workflow.
6. Čaká na beh pre tento tag a overí výsledok: verzia je vydaná a existuje GitHub Release.
   - Keď kontroly v CI zlyhajú, nič sa nevydalo ani nemergovalo. Oprava ide do release vetvy (krok 4 znova, schválenie sa môže zrušiť) a pri ďalšom spustení príkaz tag presunie (pozri „Presun tagu“).
7. **Merge do `main` až po vydaní, len vydaného commitu `H`.** Najprv overí, že vydaná verzia vznikla z `H` (pozri „Commit vydanej verzie“ v Modeli) a že nie je nižšia ako najvyššia vydaná stabilná verzia; to nemá nastať (kontrola poradia v akcii), a keby predsa, príkaz nemerguje a skončí chybou.
   - ak je hlava PR stále `H`: `gh pr merge --merge --subject "release: 3.1.0" --match-head-commit <H>`, pri potvrdenom bypasse s `--admin`,
   - ak merge odmietne stav `BEHIND` alebo konflikt: príkaz mergne `origin/main` do hlavy lokálne, verziu a index vyrieši automaticky ako v kroku 1, pushne a mergne znova. Pri inom konflikte nechá merge rozpracovaný ako v kroku 1; po vyriešení ukáže, čo riešenie zmenilo oproti automatickému výsledku, a pokračuje len po potvrdení,
   - **medzi `H` a hlavou PR smú byť len mergy `main`:** druhý rodič je predkom `origin/main` a strom sa rovná výsledku `git merge-tree --write-tree` s automatickým vyriešením verzie a indexu, alebo ide o riešenie konfliktu potvrdené v predchádzajúcom bode. Správa commitu ani trailer nerozhodujú,
   - **ak hlava PR obsahuje iné commity** (niekto po tagu pushol do vetvy alebo do nej mergol PR): príkaz ich vypíše, vytvorí z `H` novú vetvu `release-merge/3.1.0`, do nej mergne `origin/main` rovnakým spôsobom a otvorí nový PR s merge commitom. Pôvodný PR zatvorí s odkazom. Cudzie commity ostanú v pôvodnej vetve (krok 9). Menný priestor `release-merge/` nie je release vetva, `start` ani `publish` ho neponúkajú,
   - ak repo po novom pushi znova vyžaduje schválenie, príkaz čaká (bypass len po potvrdení). Verzia je vtedy už vydaná a ide o „vydaný, ale nemergnutý release“.
8. Overí, že `H` je predkom `main`. Ak nie je (PR bol po tagu mergnutý squashom alebo rebase), otvorí PR z `release-merge/3.1.0` ako v kroku 7. Ak PR niekto mergol merge commitom s inou hlavou ako `H`, príkaz vypíše commity, ktoré sa tým dostali do `main` a nie sú vo vydanej verzii, ako varovanie: vyjdú v ďalšom releasi. Nič nevracia (rozhodnutie 34).
9. **Upratanie:** worktree, lokálnu vetvu a vetvu na origine zmaže, len ak je ich hlava predkom `main`, je to hlava, ktorú mergol zlúčený release PR (pravidlo 1 pri squashi), alebo obsahuje okrem `H` len mergy `main` podľa kroku 7, a vo worktree nie sú necommitnuté zmeny ani nepushnuté commity (overí znova teraz, nie len na začiatku príkazu; zmeny mohli vzniknúť počas čakania na schválenie).
   - Inak ich nechá, vypíše necommitnuté zmeny a commity, ktoré nie sú v `main`, a `start` ich potom ponúkne ako zvyšok vydaného releasu.
   - Neverzované súbory vo worktree vypíše a zmaže ich až po potvrdení. `git worktree remove --force` sa použije len vtedy, keď okrem potvrdených neverzovaných súborov nie je vo worktree nič, lebo by potichu zahodil aj úpravy sledovaných súborov.
   - Vetvu na origine môže zmazať GitHub pri merge, ak to repo má nastavené. Vetvu `release-merge/3.1.0` po merge jej PR zmaže príkaz, ak ju nezmazal GitHub.

**Release PR mergnutý alebo zatvorený mimo nástroja** (príručka hovorí: release PR nemergujte ručne). Namiesto samostatnej cesty pre každý variant platia tri pravidlá:
1. **Mergnutý skôr, ako verzia vyšla** (pred tagom, alebo po tagu, keď beh verziu nevydal: kontroly zlyhali alebo tag bol neplatný, napríklad po squashi hneď po schválení): stav **nevydaná verzia v `main`**.
   - Príkaz ukáže, kto PR mergol a či bol schválený, a pokračuje len po potvrdení; potvrdenie zapíše do tagu (`confirmed-by`). Bez potvrdenia skončí.
   - Otaguje commit, ktorý merge dal do `main` (pri merge commite hlavu PR, pri squash alebo rebase výsledný commit v `main`); existujúci nevydaný tag naň presunie podľa „Presun tagu“. Pokračuje krokom 6. Tag je vždy v histórii `main`.
   - Ak správa tohto commitu obsahuje značku, ktorá by beh preskočila (napríklad `[skip ci]` z niektorého commitu releasu v squash správe), otaguje najbližší commit `main`, ktorý ho obsahuje a značku nemá; ak taký nie je, ide rovno cestou opravy cez vetvu `release/3.1.0` nižšie.
   - Keď kontroly v CI zlyhajú, oprava ide do vetvy `release/3.1.0`: ak zanikla, príkaz ju vytvorí znova z `main`; ak existuje, mergne do nej `origin/main`. Potom nový PR a po schválení sa tag presunie na jeho hlavu.
2. **Mergnutý po tagu merge commitom, verzia vyšla a `H` je predkom `main`:** hotovo, ako keby mergol nástroj. Commity, ktoré sa tým dostali do `main` a nie sú v `H`, vypíše ako varovanie (krok 8).
3. **Inak** (squash alebo rebase po vydaní, zatvorený bez merge): po vydaní jeden nový PR z `H` vo vetve `release-merge/3.1.0` ako v kroku 7. Zatvorený PR pred vydaním: príkaz skončí a ponúkne PR znova otvoriť alebo release zrušiť. Akcia tag finalu so zatvoreným PR nevydá; po znovu otvorení sa tag presunie po kontrolách finalu (riadok „beh skončil neplatný tag“ v tabuľke stavov).

Pri každom z troch pravidiel príkaz vypíše aj PR, ktorým GitHub po ručnom merge a zmazaní release vetvy zmenil base na `main` (udalosť `base_ref_changed`; admin-dam maže vetvy po merge), lebo ich merge by dal do `main` nevydaný kód.

**Final z `hotfix/*`:**
1. Final commit (`--no-verify`), verzia ako pri release (pri npm aj v `package-lock.json`).
2. Push (`--no-follow-tags`).
3. Pri `requireTestedPrerelease` určí kandidáta. Vytvorí anotovaný tag `2.30.2` (`release-tools: hotfix; candidate: <verzia>`) na tomto commite a pushne len tento tag (`<sha>:refs/tags/2.30.2`, `--no-follow-tags`). Push tagu spustí release workflow, ktorý spraví všetky kontroly a až potom publikuje.
4. Čaká na beh pre tento tag a overí výsledok. Keď kontroly zlyhajú (nič nevyšlo), oprava ide do hotfix vetvy a pri ďalšom spustení príkaz tag presunie (pozri „Presun tagu“).
5. **Changelog do `main`:** cez GitHub API, bez lokálneho gitu.
   1. Vetva `docs/changelog-2.30.2` z `origin/main`.
   2. Súbor z tagu `2.30.2`.
   3. Riadok v indexe `CHANGELOG.md`, zaradený podľa verzie.
   4. PR `docs: changelog 2.30.2`, merge commitom `--match-head-commit`, schválenie a bypass rovnako ako pri release PR.
   5. Ak PR konfliktuje (`DIRTY`, napríklad index po inom hotfixe) alebo je pozadu (`BEHIND`, napríklad admin-dam so `strict`, keď do `main` medzitým pribudla zmena), príkaz vetvu `docs/changelog-2.30.2` vytvorí znova z aktuálneho `main` s indexom zostaveným nanovo a PR aktualizuje.
6. Až po merge PR s changelogom zmaže vetvu `docs/changelog-2.30.2` na origine (ak ju nezmazal GitHub a ukazuje na mergnutú hlavu PR; inak ju nechá a upozorní) a vetvu `hotfix/2.30.2` na origine, worktree aj lokálnu vetvu, a len ak je ich hlava predkom tagu `2.30.2` a vo worktree nie sú necommitnuté zmeny ani nepushnuté commity; inak ich nechá a vypíše zmeny a commity za tagom (`2.30.2..hlava`) ako v kroku 9 finalu. Tag commit udrží. Obnova po prerušení sa odvodí od tagu, nie od hotfix vetvy.
7. Pripomenie: „Je chyba aj v najnovšej verzii? Sprav patch release.“

**Pre-release:**
1. Pri rc z `release/*` s `requireTestedPrerelease` najprv mergne `origin/main` do vetvy a pushne ju. Z hotfix vetvy ani z iných vetiev nikdy nemerguje.
2. Vytvorí anotovaný tag `X.Y.Z-<id>.N` (`release-tools: prerelease`) na HEAD a pushne len tento tag (`<sha>:refs/tags/…`, `--no-follow-tags`). Push tagu spustí release workflow.
3. Čaká na beh pre tento tag a overí výsledok. Keď zlyhá, oprava ide do vetvy a ďalší pre-release dostane ďalšie číslo. Vetva ostáva.

**Dev build:**
1. Navrhne verziu podľa pravidla v časti Model. Namiesto času sa dá zadať vlastný názov.
2. Vytvorí anotovaný tag (`release-tools: dev`) na HEAD a pushne len tento tag (`<sha>:refs/tags/…`, `--no-follow-tags`).
3. Čaká na beh a vypíše riadok do `package.json` projektu s URL `.tgz`, ktorú prečíta zo skutočne nahraného súboru pri GitHub Release. Vetva ostáva. Keď zlyhá, ďalší pokus dostane nový čas alebo iný názov.

**Presun tagu** (len stabilný tag finalu alebo hotfixu; pre-release a dev tagy sa nepresúvajú nikdy). Tag sa smie presunúť, aj na ten istý commit, vždy, keď **verzia nie je vydaná** (overené online v registry, pri `publish: "none"` podľa GitHub Release), aj keď job `publish` už bežal. Postup je dvojfázový, aby ho nemohol predbehnúť starý beh:
1. pôvodný anotovaný tag uloží lokálne do `refs/release-tools/moving/<tag>` (tag objekt aj s popisom) a až potom ho zmaže na GitHube,
2. zruší čakajúce behy pre tento tag a počká, kým bežiace skončia,
3. znova overí, že verzia nie je vydaná. Ak medzičasom vyšla, obnoví pôvodný tag (overí, že ukazuje na commit vydanej verzie) a dokončí vydanie,
4. až potom, v tom istom behu `release:publish` a po kontrolách finalu alebo hotfixu, vytvorí nový tag a lokálne uložený zmaže (pri zrušení nový tag nevytvára). Nový beh spraví celý build nanovo, nezávisí od artefaktov starých behov.
- **Prerušený presun alebo zrušenie** (pád CLI medzi krokmi 1 a 4) obnoví na začiatku každý príkaz z `refs/release-tools/moving/*`. **Obnova nikdy nevytvorí tag nevydanej verzie:** počká na behy a overí stav. Rozhoduje stav na GitHube a v registry, uložený tag je len záloha a nikdy neprepíše tag, ktorý na GitHube existuje:
  - **tag na GitHube existuje:** presun alebo obnovu už dokončil tento alebo iný príkaz (pád mohol prísť po pushi nového tagu a pred zmazaním uloženého refu). Uložený ref sa len zmaže a ďalej platia bežné kontroly vrátane commitu vydanej verzie;
  - **tag chýba a verzia vyšla:** tag sa obnoví na commite vydanej verzie (provenance, pri `publish: "none"` popis Release). Použije sa uložený objekt, ak ukazuje na tento commit, inak nový tag na tomto commite. Platí aj pre pre-release (obnova na vydanom commite nie je presun);
  - **tag chýba a verzia nevyšla:** zmaže sa len uložený ref a tag ostane chýbať. Nový stabilný tag potom vytvorí výhradne `release:publish` → final alebo hotfix po všetkých kontrolách (riadok „tag chýba, PR mergovateľný“); nedokončené zrušenie dokončí `start` → zrušiť. `refs/release-tools/tags/*` sa pred obnovou neprunuje (fetch s `--no-prune`). Na inom počítači pomôže riadok „verzia vydaná, tag chýba“ v tabuľke nižšie.
- **Starý beh nevydá nič iné ako commit svojho tagu,** ani keď je nový tag na tom istom commite: job `build` si zapamätá SHA tag objektu (výstup `tag-object`) a job `publish` tesne pred publikovaním aj pred vytvorením GitHub Release overí, že tag na GitHube ukazuje na presne tento tag objekt. Znovu vytvorený tag je vždy nový objekt (náhodné `id` v popise, pozri Model). Opakovanie celého starého behu („Re-run all jobs“) by v jobe `build` prečítalo už nový tag; odmietne ho horná hranica veku tagu (tag novší ako beh o viac ako 5 min, pozri „Kroky akcie“). Keď tag vznikol znova do 5 min od starého behu, opakovanie zbuildí ten istý commit a nič nepokazí (druhý publish odmietne npm a integrita sa porovná).
- Tag vydanej verzie sa nikdy nemaže ani nepresúva. Jediná výnimka je poistka pri nezhode s commitom vydanej verzie (pozri Model), po potvrdení.
- Rovnaký dvojfázový postup používa zrušenie releasu; `cleanup` zjednodušený (pozri `release:cleanup`).

**Stav a opakovanie:** príkaz nemá lokálny stav okrem tagu uloženého počas presunu. Pri každom spustení zistí stav z GitHubu (vetvy, PR, tagy, GitHub Releases, jobs API behov), npm a lokálnych worktree a pokračuje od prvého nedokončeného kroku. Za výsledok berie stav, nie výsledok konkrétneho behu.

## `release:cleanup`

1. Zostaví zoznam zo **všetkých** GitHub Releases aj tagov nástroja na GitHube (so stránkovaním):
   - dev buildy (identifikátor `dev`),
   - tagy nevydaných pre-releasov a nevydané stabilné tagy, ktorých vetva už neexistuje,
   - dokončené behy release workflowu verzie, ktorej tag už chýba a ktorá nie je vydaná (zvyšok prerušeného zrušenia alebo `cleanup`, aj tagu zmazaného ručne). Zaradí ich bez ohľadu na to, čí tag bol: beh, ktorého tag zmizol ešte pred validáciou, nemá stopu nástroja a jeho opakovanie by znova pushnutý tag vydalo. Stabilnú verziu s release vetvou nezaradí.
   - Tagy mimo nástroja (bez popisu `release-tools: …`) nikdy nezaradí. Tag vydanej verzie obnoví len podľa behu so stopou nástroja (výsledok akcie iný ako „nič na vydanie“ a „neoverený“, alebo bežal job `publish`), vo všetkých pokusoch behu.
   - Pri každej položke si zapamätá tag objekt, GitHub Release a behy. Pred mazaním overí, že sa nezmenili (tag rovnaký objekt alebo stále chýba, žiadny aktívny beh, stabilná verzia bez release vetvy), inak celú položku preskočí; tag maže s lease na zapamätaný objekt a Release len zapamätaný.
   - **Preskočí** tagy, ktoré majú čakajúci alebo bežiaci beh, a tagy mladšie ako 2 h. Akcia nevydá tag starý 1 h a viac od vytvorenia behu a staré behy zmazaného tagu sa zmažú, takže zmazaný tag sa po znovu pushnutí z cudzieho klonu nedá vydať novým behom ani opakovaním starého; medzera medzi 1 h a 2 h pokryje zaokrúhlenie aj oneskorenie behu.
2. Vypíše počty a dátum najstaršieho.
3. Spýta sa, či zmazať všetky, alebo len staršie ako zadaný počet dní.
4. Ukáže, čo zmaže, a čaká na potvrdenie.
5. Pre každú položku najprv overí stav: pri nevydanom pre-release a stabilnom tagu, že verzia nie je vydaná (vrátane draftov). Potom v tomto poradí, každé len ak ešte existuje: **zmaže dokončené behy tagu** (`DELETE /repos/{o}/{r}/actions/runs/{id}`), aby ich nikto nezopakoval, **potom tag**, a po zmazaní tagu znova overí behy (bežiaci nechá dobehnúť a dokončený zmaže) aj stav vydania; ak medzičasom vyšla, tag obnoví, prípadný draft zverejní a položku preskočí. **Až nakoniec zmaže GitHub Release** (aj s `.tgz`). Tag a Release tak držia položku v zozname, kým behy nie sú zmazané; položku bez tagu a Release drží v zozname jej beh (bod 1). Dev buildom stačí to isté bez kontroly vydania, nikdy sa nevydajú. Na konci overí, že neostalo ani jedno. Opakovanie dokončí to, čo predtým nedobehlo.

Vydané verzie (alpha, beta, rc aj stabilné) nikdy nezmaže.

## Vždy najnovšia logika

- **CLI aj akcia sa berú z `main` nástroja,** takže aj hotfix zo starého tagu použije najnovšiu logiku. Nastavenia obsahu a buildu sa pritom berú z commitu, ktorý sa builduje (pozri „Konfigurácia“).
- **Push tagu spustí workflow súbor z otagovaného commitu.** V projekte je to však len stub so spúšťačmi a `uses: …@main`, ktorý sa prakticky nemení. Samotná logika príde vždy z `main` nástroja.
- **Stub je zmluva:** akcia z `main` musí fungovať aj so staršími stubmi v tagoch hotfix línií. Prvá verzia stubu preto obsahuje všetko, čo bude neskôr potrebné (výstupy jobov, režimy).
- **Kontrola v príkazoch:** commit, ktorý dostane tag, stub obsahuje. Commity spred zavedenia nástroja (v common-admin tagy pod 2.0.0) sa otagovať nedajú.

## Workflow v projekte a akcia `publish`

**Stub `.github/workflows/release-package.yml`** (v common-admin ostáva názov súboru aj environment, takže npm trusted publisher sa nemení):
```yaml
name: Release
on:
  push:
    tags: ['[0-9]*.[0-9]*.[0-9]*']
concurrency:
  group: release
  cancel-in-progress: false
  queue: max
jobs:
  build:
    if: ${{ !github.event.deleted }}
    runs-on: ubuntu-latest
    permissions: { contents: read, actions: read, pull-requests: read }
    outputs:
      release: ${{ steps.build.outputs.release }}
      tag-object: ${{ steps.build.outputs.tag-object }}
      tarball-sha512: ${{ steps.build.outputs.tarball-sha512 }}
    steps:
      - id: build
        uses: anzusystems/release-tools/publish@main
        with: { mode: build }
  publish:
    needs: build
    if: needs.build.outputs.release == 'true'
    runs-on: ubuntu-latest
    environment: npmjs-publish
    permissions: { contents: write, id-token: write }
    outputs:
      version: ${{ steps.publish.outputs.version }}
      tag: ${{ steps.publish.outputs.tag }}
      prerelease: ${{ steps.publish.outputs.prerelease }}
      latest: ${{ steps.publish.outputs.latest }}
      published: ${{ steps.publish.outputs.published }}
      released-now: ${{ steps.publish.outputs.released-now }}
    steps:
      - id: publish
        uses: anzusystems/release-tools/publish@main
        with:
          mode: publish
          tag-object: '${{ needs.build.outputs.tag-object }}'
          tarball-sha512: '${{ needs.build.outputs.tarball-sha512 }}'
```

Prvé vydanie nového npm balíka stub zatiaľ nerieši (pozri „Prvé vydanie nového npm balíka“).

**Variant pre `publish: "none"`:** job `publish` bez `environment` a s `permissions: { contents: write }`. Nasadenie sa pripojí ako ďalší job s `needs: publish` a výstupmi vyššie. `init` zapíše správny variant.

**Dva joby jednej akcie:**
- **`build`** (bez environmentu a bez `id-token`, s nastaveniami z commitu): validácia, inštalácia, `ci.setup`, `ci.checks`, build, balenie a overenie balíka. Výsledok je `.tgz` a text popisu GitHub Release ako artefakt behu; hash `.tgz` a SHA tag objektu idú ako výstupy jobu.
- **`publish`** (environment a `id-token`, pevné prostredie od nástroja, bez checkoutu projektu): Node, ktorý určí nástroj, overenie npm ≥ 11.5.1, stiahne artefakt, overí hash z výstupu `build`, overí, že tag na GitHube stále ukazuje na tag objekt z výstupu `build`, spustí `npm publish`, overí commit vydanej verzie a vytvorí GitHub Release.
- **Rozhodnutia počíta job `publish` sám:** npm tag, `prerelease` a `latest` vypočíta z tagu a registry. Z artefaktu jobu `build`, v ktorom beží kód projektu (`ci.checks`, build), berie len `.tgz` (manifest overí znova) a text popisu.
- Kód vetvy a závislostí ani nastavenia z commitu tak nikdy nebežia v jobe, ktorý môže publikovať na npm.

**Spúšťače:**
- `push` tagu verzie: jediný spúšťač. Pri tagu, ktorý nie je tagom nástroja (formát a popis `release-tools: …`), akcia skončí „nič na vydanie“. Zmazanie tagu podľa e2e (25. 9. 2026) žiadny beh nevytvorí; podmienka `if: !github.event.deleted` ostáva ako poistka, keby GitHub beh predsa spustil (oba joby by sa preskočili).
- `workflow_dispatch` stub nemá. Chýbajúci GitHub Release vydanej verzie dorobí CLI.

**`concurrency`:** všetky behy sú v jednej fronte s `queue: max`. Fronta je podľa dokumentácie FIFO a pojme najviac 100 čakajúcich behov; ďalšie GitHub zruší. Zrušený beh tagu CLI rozpozná (riadok „žiadny beh alebo bol zrušený“ v tabuľke stavov). Na poradí nezáleží, každý beh overuje stav sám.

**Checkout** vždy `github.sha` (commit tagu) s `fetch-depth: 0`. Opakovaný beh builduje presne pôvodný commit a pred publikovaním overí, že tag medzitým nevznikol znova (rovnaký tag objekt).

**Anotovaný tag sa číta cez API, nie z checkoutu:** `actions/checkout` v4 a v5 stiahne tag ako lightweight a popis by sa stratil. Akcia načíta `GET /repos/{o}/{r}/git/ref/tags/X`, pri objekte typu `tag` `GET /repos/{o}/{r}/git/tags/<sha>` (popis a cieľ), cieľ rekurzívne dereferencuje na commit a s `github.sha` porovnáva až tento commit.

**Composite action beží ako kroky v jobe projektu.** Npm pri trusted publishing preto uvidí workflow projektu. Tvrdenie o `workflow_ref` pre composite action je overené len v dokumentácii npm; potvrdí ho prvé ostré rc.

**Bezpečnosť:** vstupy sa odovzdávajú cez `env` a overujú regexom, nikdy sa nevkladajú priamo do `run:`.

**Kroky akcie:**
1. **Stav:** pre verziu a tag zistí `{vydaná verzia, npm tag, GitHub Release}` a či tag na GitHube existuje a (po dereferencovaní) ukazuje na `github.sha`. Ak nie (tag presunutý alebo zmazaný), job `build` skončí „nič na vydanie“: nevie už, čí tag beh spustil, a taký beh nesmie byť stopou nástroja. Job `publish` v tej situácii skončí „neplatný beh“, lebo tag už overil `build`. Chyba pri čítaní tagu (napríklad 502) skončí „neoverený“ (`unverified`); job zlyhá a dá sa zopakovať, ale ani tento beh nie je stopou nástroja. SHA tag objektu odovzdá ako výstup `tag-object`.
   - **Vek tagu:** vytvorenie behu (`created_at` z `GET /actions/runs/{id}`, pri opakovaní behu sa nemení; `/attempts/{n}` vracia čas pokusu) mínus dátum v tagu (tagger) musí byť menej ako 1 h a nesmie byť záporné o viac ako 5 min (tag vzniká pred pushom).
     - Tag starý 1 h a viac je starý tag pushnutý znova (napríklad zmazaný tag z klonu kolegu cez `push.followTags`): akcia skončí „neplatný tag“, tag ostane bez vydania a zmaže ho `cleanup`.
     - Tag novší ako beh o viac ako 5 min znamená opakovanie celého starého behu po znovuvytvorení tagu: akcia skončí „neplatný beh“.
     - Platí pre všetky druhy tagov. Výnimka: už vydaná verzia (napríklad obnovený tag pri presune). Pri nej beh nič nevydá a chýbajúci GitHub Release pri npm dorobí CLI, lebo beh nemá balík, s ktorým by obsah na npm porovnal (draft zverejní CLI).
     - Testy pokrývajú hodnoty tesne pod hranicou, presne na nej a tesne nad ňou.
   - Ak je verzia už vydaná: job `build` nič nebuilduje ani nekontroluje, len odovzdá, že treba dorobiť GitHub Release. Existujúca verzia sa nikdy nepublikuje znova.
2. **Validácia podľa druhu z popisu tagu** (druh sa zároveň overí z verzie):
   - **final:** stabilná verzia vyššia ako posledná vydaná stabilná verzia; posledná vydaná verzia najnovšej línie (jej tag) je predkom commitu (počas bootstrapu sa preskočí); `package.json` má verziu tagu; changelog existuje; **release PR z popisu tagu** je otvorený s base `main` a `github.sha` je predkom jeho hlavy, alebo je mergnutý a `github.sha` je predkom `main`. Inak ide o znovu pushnutý starý tag (napríklad z klonu kolegu cez `push.followTags`) a akcia skončí „neplatný tag“;
   - **hotfix:** stabilná verzia nižšia ako posledná vydaná stabilná verzia; je presne nasledujúci patch poslednej vydanej verzie svojej línie a tag tej verzie je predkom commitu; **žiadny tag vydanej stabilnej verzie vyššej línie nie je predkom commitu** (hotfix nesmie obsahovať novší kód); `package.json` má verziu tagu; changelog existuje; na GitHube existuje vetva `hotfix/X.Y.Z` a obsahuje `github.sha`, alebo PR s changelogom hotfixu už je v `main` (inak „neplatný tag“);
   - **pre-release:** formát `X.Y.Z-(alpha|beta|rc).N`; stabilná `X.Y.Z` ešte nie je vydaná; pri pre-release staršej línie (hotfix) rovnaká kontrola predkov ako pri hotfixe, teda žiadny tag vydanej stabilnej verzie vyššej línie nie je predkom commitu;
   - **dev:** formát `<základ>-dev.<čas|názov>` alebo `<základ pre-release>.dev.<čas|názov>`, celá verzia je platný semver;
   - pri všetkých: manifest v `.tgz` podľa „Manifest v zabalenom `.tgz`“ (kontroluje sa v kroku 4).
3. **Build** (job `build`, všetko s `ci.env`):
   - checkout `github.sha`, `setup-node` podľa konfigurácie z commitu, `corepack enable` (prípadne doinštalovať),
   - inštalácia so zamknutým lockfile, bez skriptov, ak `installScripts` nie je `true`,
   - `ci.setup`, potom `ci.checks` (okrem dev buildu),
   - pri pre-release a dev builde `npm pkg set version=…`,
   - build príkaz z konfigurácie.
4. **Balenie a overenie balíka** (job `build`). Pri `publish: "none"` sa preskočí.
   - Balenie do explicitného názvu `.tgz` a výpočet hashu.
   - Manifest v `.tgz` (`name`, `version`, `repository.url`, `private`, povolené kľúče `publishConfig`) podľa „Manifest v zabalenom `.tgz`“.
   - `pack.verify`, ak je nastavené.
   - Pri stabilnej verzii s `requireTestedPrerelease`: porovnanie s kandidátom z popisu tagu (kandidát musí byť vydaný).
5. **npm** (job `publish`): overí hash artefaktu z výstupu `build`, znova manifest v `.tgz` a že tag ukazuje na tag objekt z `build`. **Tesne pred `npm publish`** (pri `publish: "none"` pred vytvorením Release) znova overí podmienky poradia z kroku 2 proti čerstvému stavu registry (final vyššia ako posledná vydaná stabilná, hotfix nasledujúci patch svojej línie, pre-release len pred vydaním svojej stabilnej verzie), lebo opakovaný job `publish` („Re-run failed jobs“) job `build` nespustí; inak skončí „neplatný beh“. Potom publikuje podľa „Publikovanie“. Preskočí sa, ak je verzia už vydaná. Pri hláške „cannot publish over previously published version“ porovná `dist.integrity` s `.tgz`: pri zhode pokračuje, pri nezhode skončí chybou a GitHub Release nevytvorí. Dev build na npm nejde, pri `publish: "none"` sa krok preskočí.
6. **GitHub Release:** znova overí tag (rovnaký tag objekt ako v `build`; `--verify-tag` overuje len existenciu) a pri npm, že vydaná verzia vznikla z `github.sha` (provenance, pozri „Commit vydanej verzie“). Potom `gh release create <tag> --verify-tag` s popisom z artefaktu (obsah changelogu, odkaz na súbor pri tagu, commit a `run_id` behu; pri pre-release bez changelogu vetva, commit a „no changelog yet“), `--prerelease` alebo `--latest=true|false`; `--latest=true` len vtedy, keď je verzia v tej chvíli najvyššia vydaná stabilná verzia. Job `publish` nemá checkout, preto nastaví `GH_REPO`.
   - relatívne odkazy v changelogu sú už v artefakte prepísané na absolútne pri tagu, lebo v popise GitHub Release relatívne odkazy nefungujú,
   - pri dev builde je popisom vetva, commit a riadok do `package.json` projektu, a `.tgz` sa priloží ako súbor releasu,
   - ak už existuje publikovaný, preskočí sa; ak existuje draft s rovnakým `tag_name` (job `publish` má `contents: write`, drafty vidí), nič s ním nerobí a skončí „GitHub Release dokončí CLI“. Drafty zverejňuje len CLI.
7. **Overenie registry (len upozornenie, po kroku 6):** `dist.integrity` verzie v registry sa rovná `sha512` zabaleného `.tgz` a npm tag ukazuje, kam má. Nesúlad sa vypíše do súhrnu behu ako upozornenie; release sa tým nezablokuje. Zlý npm tag opraví DevOps ručne (OIDC podporuje len `npm publish`).
8. **Súhrn behu:** odkazy na npm, tag a GitHub Release. Výstupy `version`, `tag`, `prerelease`, `latest`, `published` a `released-now` pre ďalšie joby (význam pozri pri `publish: "none"`).

**npm tag a príznak Latest:**
- pre-release → `alpha`, `beta`, `rc`, ak je vyššia ako verzia, na ktorú tag ukazuje; inak a pri hotfix línii `<id>-X.Y`; GitHub Pre-release;
- dev build → na npm nie je, GitHub Pre-release s `.tgz`;
- final → `latest`, GitHub Latest (vďaka kontrole poradia v kroku 5 je vždy najvyššia vydaná stabilná verzia);
- hotfix staršej línie → `latest-X.Y`, `--latest=false`.

Akcia vždy posiela `--tag`, takže sa `latest` nikdy neposunie omylom.

Vzorky všetkých starých formátov popisu tagu a textu Release. Repo bez `main`. `init` s prerušením po každom zápise | každý push |

Vzorový projekt pre yarn 4 a pnpm | lokálne, pred každou zmenou `main` nástroja; v CI nebeží |

**Sandbox pre e2e:**
- **Názov** je v env `RELEASE_E2E_REPO`, predvolene `anzusystems/release-tools-sandbox`.
- **Ak repo neexistuje,** setup ho vytvorí cez `gh repo create` ako **verejné** repo (environmenty s pravidlami sú pri súkromných repách len v platenom pláne GitHubu a Actions sú pri verejných zadarmo; v sandboxe nie sú žiadne tajné údaje). Ak na to token nemá práva, skončí so správou, že repo treba vytvoriť ručne a zapísať do env.
- **Nastavenia sandboxu** zodpovedajú bežnému projektu: ruleset s povinným schválením aj bez neho, klasická ochrana vetvy so `strict`, environment. Testovací používateľ má bypass, aby sa sandbox dal vrátiť do východiskového stavu.
- **Jeden účet:** e2e beží pod účtom vlastníka (admin organizácie), druhý účet nie je. GitHub nedovolí schváliť vlastný PR, preto:
  - e2e automaticky overuje čakanie na schválenie a bypass po potvrdení (s právom),
  - skutočné schválenie iným používateľom a jeho zrušenie novým pushom je voliteľný interaktívny scenár (`RELEASE_E2E_APPROVER=manual`): test vypíše odkaz na PR a čaká, kým ho schváli kolega; bez neho sa scenár preskočí,
  - stav bez práva na bypass a schválenie od iného používateľa overujú integračné testy s falošným GitHubom.
- **Pred každým scenárom** sa sandbox vráti do východiskového stavu: `main`, vetvy, tagy, GitHub Releases, otvorené PR a falošné registry.
- **Spúšťajú sa lokálne** s tvojím prihláseným `gh`, žiadny token v CI netreba.

**Falošné registry:** v testovacom režime (`RELEASE_TOOLS_REGISTRY=mock`) CLI aj akcia namiesto npm používajú tagy v sandboxe:
- `npm publish` len vypíše, čo by publikoval, vytvorí tag `mock-npm/versions/<verzia>` a uloží tarball ako súbor GitHub Release `mock-npm/versions/<verzia>` (kvôli porovnaniu s kandidátom);
- npm tag je tag `mock-npm/tags/<tag>`;
- `npm view` číta tie isté tagy (`git ls-remote`).

Vlastný menný priestor `refs/mock-npm/…` GitHub nemusí prijať, preto sú to bežné tagy. Spúšťač workflowu (`[0-9]*…`) na ne nereaguje. Zvyšok akcie beží naozaj.

**Matica príkazov** (každý riadok je aspoň jeden e2e test):

| príkaz | varianty |
|---|---|
| `start` | patch, minor, major, vlastná verzia, hotfix staršej línie, hotfix inej verzie, bootstrap (bez tagov aj s tagmi bez stubu), zrušenie (aj s nevydaným stabilným tagom; vydaný release a nevydanú verziu v `main` zrušiť odmietne; prerušené zrušenie nevytvorí tag), opakovanie po čiastočnom `start`, nevydaná verzia v `main` (odkáže na `publish`), bootstrap s nevydanou verziou v `package.json` bez release PR (prvý final prejde), zvyšok vydaného releasu (mergnúť do nového, zmazať po potvrdení) a zvyšok hotfixu (len do nového hotfixu línie), repo bez povoleného merge commitu alebo s merge queue (odmietne) |
| `publish` | final z `release/*` (kontroly zelené aj červené, s presunom tagu), final z `hotfix/*`, alpha, beta a rc z release vetvy, z hotfix vetvy aj z inej vetvy, dev s časom, dev s vlastným názvom, dokončenie vydaného, ale nemergnutého releasu, dorobenie chýbajúceho GitHub Release z CLI |
| `cleanup` | dev buildy, tagy nevydaných pre-releasov a nevydané stabilné tagy: všetky, staršie ako N dní, nič na zmazanie, dokončenie po čiastočnom zmazaní, tag s čakajúcim alebo bežiacim behom a tag mladší ako 2 h sa preskočí, poradie kontrola stavu → behy → tag → Release |

| `publish: "none"` | final, hotfix, pre-release a dev bez npm; výstupy akcie cez `needs:`; staré Releases s lightweight tagmi sa počítajú ako vydané; draft Release po zmazaní tagu sa zverejní |
| schválenie a merge | čakanie na schválenie pred tagom, bypass po potvrdení (s právom v e2e, bez práva v integračných testoch; cez ruleset aj klasickú ochranu), schválenie kolegom a jeho zrušenie novým pushom (interaktívne, `RELEASE_E2E_APPROVER=manual`), `BEHIND` a konflikt pri čakaní, merge po vydaní, keď sa `main` medzitým pohol (lokálny merge s konfliktom verzie a indexu, iný konflikt s potvrdením), PR otvorený do release vetvy po tagu (kontrola pred merge aj pred zmazaním vetvy), zrušenie hotfixu s otvorenými PR do jeho vetvy, worktree s necommitnutými zmenami po vydaní ostane, vetva `release-merge/` sa po merge zmaže, bypass cez `exempt`, admin a lineárna história z `branchProtectionRule`, merge `main` s pridanou zmenou sa neprijme, cudzí commit vo vetve po tagu (nový PR z `H`, vetva ostane), ručný merge release PR pred tagom (s potvrdením aj bez neho, aj so zlyhanými kontrolami a opravou cez novú vetvu z `main`), po tagu merge commitom s cudzím commitom (varovanie), squash a rebase po tagu, zatvorený PR pred vydaním aj po ňom |
| overenie balíka | `requireTestedPrerelease` zhoda aj nezhoda, zafixovaný kandidát pri novom rc počas behu, `pack.verify`, manifest v `.tgz` zmenený buildom, nepovolený kľúč `publishConfig` (aj `@x:registry`), premenné `npm_config_*` v ľubovoľnej veľkosti písmen |
| tagy | znovu pushnutý zmazaný tag každého druhu (final, hotfix, pre-release, dev) sa nevydá, ani opakovaním starého behu („Re-run“) po zrušení alebo `cleanup`, aj po ich prerušení; žiadny príkaz nevytvorí lokálny tag (`fetch --no-tags --refmap=`, aj s `remote.origin.fetch` pre tagy) ani nezmaže cudzie refy (aj s `fetch.prune=true` a vlastným refspecom pre PR); starý beh po znovuvytvorení tagu na tom istom commite nič nevydá, dvojfázový presun proti súbežnému opakovaniu starého behu, pád CLI počas presunu (dokončenie z uloženého tagu aj z iného počítača), vydaná verzia z iného commitu zastaví Release aj merge (presun tagu po potvrdení), vydaná verzia bez provenance (po potvrdení), obnova prerušeného presunu aj zrušenia nevytvorí nový tag, vek tagu tesne pod, na a nad 1 h, tag novší ako beh (opakovanie celého starého behu), nový tag v tej istej sekunde má iné SHA, beh zo zmazania refu na hlave `main` sa nezaráta, `cleanup` proti čakajúcemu behu, `[skip ci]` a `skip-checks: true` v otagovanom commite, tagy mimo nástroja sa ignorujú, anotovaný tag po checkoute bez popisu |
| vydanie nástroja | prvý bootstrap `main`, vydanie nástroja ako `publish: "none"` (`build: false`), dlho bežiaci príkaz CLI N−2 a N−1, ktorý otaguje až po merge release PR nástroja (akcia N), CLI N−1 dokončí merge nad Release od akcie N, `build` N−2 proti `publish` N, nepodporovaná schéma artefaktu, výmena priečinka balíka v cache npx počas čakania, vzorky starých formátov, `package.json` nástroja bez skriptov inštalácie |
| všetky | `--dry-run` nič nezmení; žiadny príkaz nepushne `main` ani lokálny tag (aj s `push.followTags=true`) |

**Riadené prerušenie:** v testovacom režime `RELEASE_TOOLS_FAIL_AT=<krok>` ukončí príkaz alebo akciu hneď po danom kroku. Kroky sú napríklad final commit, push, vytvorenie PR, push tagu, build, publish, GitHub Release a merge. Test pre **každý krok**:
1. spustí príkaz s prerušením,
2. overí, že stav nie je rozbitý:
   - verzia, ktorá nie je vydaná, sa dá vydať znova,
   - tag vydanej verzie sa nepohol,
   - nič nie je zmazané predčasne,
3. spustí príkaz znova bez prerušenia,
4. overí, že sa dokončil a nič neprebehlo dvakrát.

Prerušenia sa v e2e reťazia v jednom vydaní (`FAIL_AT=krok1`, potom opakovanie s `FAIL_AT=krok2` atď.), aby sa nečakalo na CI pri každom kroku zvlášť. Opakovanie jobu `publish` s artefaktom z predošlého pokusu (`--failed`) sa overí v e2e.

Tým sa overí, že nemôže nastať situácia „polovica skriptu prebehla, tag existuje a verziu už nejde vydať“.

**Scenáre** (integračné všetky, e2e hlavné cesty):
- **start:**
  - patch, minor, major a vlastná verzia,
  - verzia, vetva alebo priečinok už existuje; vlastný čiastočný stav sa dokončí (aj lokálna vetva bez worktree),
  - vydaný, ale nemergnutý release (odmietne),
  - bootstrap,
  - hotfix, ktorý nie je posledný patch, je v najnovšej línii, nie je nasledujúci patch alebo jeho tag nemá stub; posledný patch sa počíta z vydaných verzií, nie z tagov.
- **final:**
  - PR nie je mergovateľný: čakanie, schválenie, bypass po potvrdení, `BEHIND` a konflikt,
  - release PR mergnutý ručne pred tagom: `start` odkáže na `publish`, kontrola verzie s rovnosťou, potvrdenie pred tagom; po zlyhaní kontrol oprava cez vetvu z `main`; squash hneď po schválení (tag sa presunie na commit v `main`); squash so značkou `[skip ci]` v správe; ručný merge počas zrušenia; PR presmerované GitHubom na `main` po ručnom merge,
  - prvý final nového projektu s verziou rovnou `main` (bootstrap),
  - `released-now` po páde runnera a „Re-run failed jobs“; job nasadenia v e2e overuje, že verzia je stále Latest,
  - PR presmerované GitHubom na `main` sa vypíšu pri každom z troch pravidiel ručného merge,
  - PR s changelogom hotfixu v stave `BEHIND`, pomocná vetva sa po merge zmaže,
  - bootstrap: nevydaná verzia v `main` bez mergnutého release PR nie je stav „nevydaná verzia v `main`“,
  - cudzie commity vo vetve po vydaní: vetva a worktree ostanú, `start` ich ponúkne ako zvyšok,
  - kontroly v CI zlyhajú: nič sa nevydá ani nemergne, po oprave sa tag presunie,
  - starý beh po presune tagu nič nevydá, ani po znovuvytvorení na tom istom commite,
  - zlyhaný job `publish` finalu 3.0.1, potom vydaný 3.1.0 a opakovanie behu 3.0.1: nič sa nevydá a `latest` ostane na 3.1.0; final 3.1.0 sa neotaguje, kým tag 3.0.1 nie je dokončený alebo zrušený,
  - vlastná verzia `3.1.0-beta.1` alebo `3.1.0+build` v `start` sa odmietne,
  - urgentný patch 3.0.1, keď kontroly finalu 3.1.0 zlyhali: stiahnutie tagu 3.1.0, vydanie 3.0.1, potom nový final 3.1.0,
  - **dva releasy v oboch poradiach:** `3.0.1` a potom `3.1.0`; `3.1.0` a potom `3.0.1` (druhý final skončí pred akoukoľvek zmenou); druhý final sa neotaguje, kým beží alebo čaká beh prvého,
  - vydaný, ale nemergnutý release blokuje ďalší final,
  - merge po vydaní, keď sa medzitým pohol `main` (v `doc/`),
  - otvorené PR do release vetvy,
  - changelog inej nevydanej verzie vo vetve,
  - prerušenie po každom kroku a nové spustenie.
- **akcia:**
  - obnova po čiastočnom vydaní: verzia na npm bez GitHub Release (bez nového buildu), „cannot publish over previously published version“ so zhodnou aj inou integritou,
  - job `publish` zlyhal pred publikovaním: opakovanie s tým istým artefaktom aj presun tagu na ten istý commit s novým buildom (napríklad po 30 dňoch),
  - `publish: "none"`: GitHub Release chýba, verzia sa berie ako nevydaná a tag sa vytvorí znova; vydaný pre-release sa počíta ako vydaný (`cleanup` ho nezmaže, final nájde kandidáta); draft Release po zmazaní tagu,
  - pre tag neexistuje žiadny beh,
  - viac behov naraz vo fronte (`queue: max`), do 100 sa nič nezruší; zrušený beh tagu CLI rozpozná,
  - tag bez popisu nástroja a tag v inom formáte: nič na vydanie,
  - `ci.checks` zlyhajú: nič sa nevydá, job `publish` nebeží,
  - verzia vnútri `.tgz` nesedí,
  - `pack.verify`: iný súbor v `dist/`, chýbajúci súbor, nepovolený súbor mimo `dist/`,
  - final, ktorý neobsahuje predchádzajúci release; hotfix, ktorý obsahuje tag vyššej línie; pre-release staršej línie s kódom vyššej línie; rovnaká kontrola predkov v CLI pred tagom z hotfix vetvy,
  - overenie registry po publikovaní hlási nesúlad: len upozornenie.
- **pre-release:**
  - číslovanie `beta.1`, `beta.2`, `rc.1` súčasne, aj podľa verzií na npm bez tagu,
  - pre-release už vydanej stabilnej verzie sa odmietne,
  - npm tag sa neposunie späť; pre-release hotfixu dostane `<id>-X.Y`,
  - zlyhaný build: ďalší pokus dostane ďalšie číslo, tag sa nepresúva,
  - rc pred finalom z `release/*` mergne aktuálny `main`; rc z hotfixu nikdy.
- **dev:**
  - názov z najbližšieho tagu na GitHube, preskakovanie dev tagov, vetva bez tagu, lokálne tagy bez vplyvu,
  - vlastný názov, obsadený názov, neplatný názov (`01`),
  - dev tag sa nikdy nepresunie; beh po `cleanup` tag znova nevytvorí; zmazaný dev tag pushnutý znova sa nevydá (vek tagu),
  - cleanup nezmaže vydané verzie.
- **hotfix:**
  - zo starého tagu, build podľa konfigurácie z tagu,
  - s `requireTestedPrerelease` bez rc (odmietne) a s rc,
  - npm tag `latest-X.Y` a nezmenený príznak Latest,
  - zlyhané kontroly: presun tagu po oprave,
  - zrušenie po zlyhaní: nevydaný stabilný tag sa zmaže a 2.30.2 sa dá začať znova,
  - PR s changelogom do `main` vrátane čakania na merge,
  - prerušenie po pushi tagu.
- **zrušenie** releasu s otvorenými PR (presmerovanie), s necommitnutými zmenami, prerušené v polovici.
- **stav vetvy:** necommitnuté zmeny, nepushnuté commity, rozídené vetvy, neverzované súbory vo worktree pri upratovaní.
- **konflikty a „treba si stiahnuť zmeny“** (situácie z gitflow); príkaz musí zlyhať ešte pred akoukoľvek zmenou a povedať, čo spraviť:
  - rozpracovaný merge vo worktree s nevyriešeným konfliktom (`MERGE_HEAD`, konfliktné súbory),
  - omylom commitnuté konfliktné značky (`<<<<<<<`, `=======`, `>>>>>>>`) v zmenených súboroch,
  - lokálna vetva je pozadu, lebo niekto medzitým mergol PR do release vetvy na GitHube: stiahne sa fast-forward, alebo príkaz povie, že si treba zmeny stiahnuť,
  - lokálna a vzdialená vetva sa rozišli,
  - `main` sa zmenil tak, že merge do releasu konfliktuje,
  - rovnaký tag alebo verziu medzitým vytvoril niekto iný: push tagu sa odmietne a nič nezostane rozrobené,
  - vetva na origine medzitým zmizla,
  - worktree bol zmazaný ručne, vetva ostala.

## Nastavenia (raz, ručne)

Nástroj nastavenia repa nerieši ani nemení. Pre fungovanie potrebuje len to, čo je v „Čo nástroj potrebuje od repa“.

**`anzusystems/release-tools`:**
1. Verejné repo.
2. Bootstrap `main`: jeden commit priamo do `main` (README, LICENSE), potom jednorazový PR s prvou implementáciou (pozri „Distribúcia nástroja“).
3. Env `RELEASE_E2E_REPO` lokálne; sandbox repo vytvorí setup testov, ak ešte neexistuje.

**common-admin:**
1. **Merge commit** povolený (dnes je).
2. **Git e-mail** vývojárov, ktorí vydávajú, priradený ku GitHub účtu (dnes lokálny e-mail vlastníka nie je; commity by kvôli pravidlu „extra approval for unattributed changes“ potrebovali ďalšie schválenie).

4. **npmjs.com:** skontrolovať trusted publisher (repo, `release-package.yml`, environment `npmjs-publish`).
5. **Ruleset pre tagy:** nepridávať (rozhodnuté). Tagy vytvára príkaz; tag finalu a hotfixu, ktorý neprešiel kontrolami, musí vedieť presunúť a `cleanup` musí vedieť mazať nevydané tagy. Tagy vydaných verzií príkaz nikdy nemaže ani nepresúva. Prípadné zneužitie alebo náhodné znovu pushnutie tagu obmedzuje validácia v akcii (vek tagu, predkovia, stav release PR alebo hotfix vetvy, hotfix len ako nasledujúci patch) a nastavenie na npmjs.com (pozri „Úlohy pre DevOps“).

## Riziká a čo sa zaručiť nedá

- **Výpadky GitHubu, npm alebo siete** zaručiť nevieme. Každý krok sa však dá spustiť znova a npm publish je len jeden krok v CI po všetkých kontrolách.
- **Konflikty pri merge `main` do releasu** (okrem verzie a indexu) musí vyriešiť človek. Príkaz nechá merge rozpracovaný a po commite pokračuje.
- **Po vydaní môže merge do `main` čakať** (schválenie po novom pushi, konflikt). Verzia je vydaná, `main` zaostáva a nástroj ďalší final nepustí, kým merge nedobehne. Stav „nedá sa vydať a nedá sa pohnúť“ tým nevzniká.
- **Zmena v `main` nástroja platí hneď pre všetky projekty.** Chyba, ktorú testy nezachytia, zasiahne všetky naraz. Ochranou sú testy vrátane e2e, ktoré sa spustia pred každou zmenou `main`. Ochranu `main` nástroja plán nerieši (rozhodnuté). Chyba, ktorá blokuje vydávanie, sa opraví núdzovo priamo v `main` nástroja (pozri „Distribúcia nástroja“).
- **Cudzie commity v `main`:** keď niekto release PR po tagu ručne mergne merge commitom aj s commitmi pushnutými po tagu, tie sú v `main`, hoci nie sú vo vydanej verzii. Nástroj ich vypíše ako varovanie a vyjdú v ďalšom releasi (rozhodnutie 34).
- **Validácia v akcii nie je bezpečnostná hranica.** Kto má právo zápisu, môže pushnúť tag. Obmedzujú to:
  - oddelený job `build` bez `id-token` a job `publish` bez checkoutu projektu a s pevným prostredím,
  - validácia predkov (final obsahuje predchádzajúci release, hotfix neobsahuje vyššiu líniu) a hotfix len ako nasledujúci patch,
  - nastavenie na npmjs.com z „Úlohy pre DevOps“.
- **Neoverené:**
  - **Trusted publishing** cez composite action a `npm publish <súbor.tgz>` na strane GitHubu (`workflow_ref`). Kód npm to podporuje; potvrdí to prvé ostré rc.
  - **`github:` pri npx** na skutočnom GitHube (lokálne overené s `git+file` a s `github:npm/ini`).
  - **Inštalácia dev buildu z URL cez yarn 4** vrátane presmerovania. Overí ju krok 8 zavedenia.
  - **Artefakt z predošlého pokusu** pri `gh run rerun --failed`: GitHub ho výslovne nezaručuje. Obnova naň nespolieha (po zlyhaní opakovania sa tag presunie a build sa spraví nanovo); e2e to overí.
  - **Znovu vytvorený tag na tom istom commite** spustí nový beh; overí e2e.
  - **GitHub Release po zmazaní tagu** prejde do draftu (komunitné zdroje, nie dokumentácia). Týka sa počítania vydaných verzií pri `publish: "none"`; e2e to potvrdilo (25. 9. 2026).
  - **Provenance pri composite action** obsahuje commit projektu (`gitCommit`); overené na cudzom balíku, potvrdí prvé ostré rc.
  - **Webhook Azure** pri GitHub Release vytvorenom cez `GITHUB_TOKEN` overí prvý release admin-dam.
- **Hotfix worktree zo starého tagu:** inštalácia môže trvať 1–2 min a pri yarn je zdieľanie cache cez `YARN_CACHE_FOLDER` neoverené.
- **Hotfixy verzií spred zavedenia nástroja nie sú podporované,** lebo ich tagy neobsahujú stub workflow.
- **Pomalý GitHub:** všetky čakania na GitHub (PR, beh workflowu, API) v nástroji aj v testoch majú štedrý časový limit a pri chybe siete alebo limitu API to skúsia znova.
- **Opakovanie behu** GitHub dovolí len 30 dní. Neskôr sa tag vytvorí znova (ak nič nevyšlo). Chýbajúci GitHub Release vydanej verzie dorobí CLI vždy, bez opakovania behu.
- **Schválenie po pushi:** commity nástroja s e-mailom, ktorý GitHub nepozná, môžu kvôli pravidlu „extra approval for unattributed changes“ vyžadovať ďalšie schválenie; `start` na to upozorní.
