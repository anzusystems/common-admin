1. **(A) High — deliberate test expectation, not established product intent.** The test introduced in `03c3a108` explicitly expected a later widget to reopen the running upload and finish “Save and apply”; its comment says that expectation was inferred from code before the test ran. OP9-L2 deliberately reverses it. See `W/__tests__/consumerProfileImageWidgetUpload.test.ts:748`. **Smallest fix: M** — offer an explicit way to resume an upload for the same record, while keeping automatic reopening disabled.

2. **(A) High — CMS return path loses completion.** During the fullscreen upload, a room kick or failed rejoin sends the editor from article edit to detail (`admin-cms/src/domains/cms/article/composables/articleEditCollab.ts:208,218`). Browser navigation can also leave and return to the keyed view (`admin-cms/src/App.vue:32`). The upload continues, but on returning the editor no longer sees its dialog or gets to apply that file; on opening another article, the editor gains protection from an old dialog appearing there. The pin button is behind the fullscreen dialog, so pinning is not an ordinary trigger for this case. **Fix: M**, as above.

3. **(A) Medium — UGC return path has the same tradeoff.** Browser Back/Forward, or switching blogs via navigation to `/` (`admin-ugc/src/domains/blog/blog/components/ActiveBlogSelect.vue:37`; `admin-ugc/src/App.vue:27`), remounts the article’s `queue-key="article"` widget (`ArticleEdit.vue:132`). Returning to that article loses the old completion path; entering another article gains protection from an unrelated upload dialog. **Fix: M**, tied to the record being edited.

4. **(B) Critical — confirmed wrong-file application.** Unmount clears only the dialog key (`dam/uploadQueue/components/UploadQueueDialogSingle.vue:93`); the old row remains. A later upload with the same key appends a row (`uploadQueuesStore.ts:242-255`), but the single dialog displays `items[0]` (`UploadQueueDialogSingle.vue:63-69`). “Save and apply” maps all rows in order (`:141-179`), and both widgets take `items[0]` (`W/components/ImageWidgetInner.vue:886`; `ImageMediaWidgetInner.vue:1058`). Once the old row is uploaded, an editor can upload a new photo and apply the **old photo**. 236 makes this easier: returning no longer exposes the old row for completion or stopping. **Fix: M** — bind a single upload dialog and its apply result to the specific newly added row; provide separate recovery for retained rows.

5. **(C) Medium — yes, the gallery dialog has the analogous stale key.** Its unmount hook clears `uploadQueueDialogSaving` only (`dam/uploadQueue/components/UploadQueueDialog.vue:110-112`). Leave a gallery or asset list during upload, then mount another widget with the same queue key: the old dialog opens. **Smallest fix: S** — clear `uploadQueueDialog` on unmount when it still names this queue; retain the upload and rows.

6. **(D) High — c2 keeps only one saved answer across pages.** `W/utils/imageSaves.ts:85-86,113-116` stores a global last answer for an image, then rejects it if its page differs. If page A has a slow save, page B saves the same image, and A answers last, a copy on B cannot take B’s saved texts; confirming its stale metadata can overwrite them. Store the last answer and answer count per page. The page filter does prevent ordinary cross-page waiting; I found no normal CMS/UGC path that waits for another page’s save.

7. **(D) Low — waits can accumulate during a stalled save.** Each “Edit metadata” opening adds a waiter (`W/utils/imageSaves.ts:100-106`); closing the dialog does not remove it (`ImageWidgetInner.vue:323-330`, similarly the media widget). Repeated open/close while a request never settles grows the retained note, and an open dialog waits indefinitely. Cancel a waiter when its opening closes. For **235**, the image, video and podcast widget paths set the intended type; I found no ordinary editor path that changes their metadata title within one opening. The two upload dialogs still change title from “Uploading” to “Upload complete” (`UploadQueueDialogSingle.vue:224-234`, `UploadQueueDialog.vue:231-241`), contrary to rule 5; the implementation note identifies this as pre-existing.

8. **(E) Low — verification and documentation gaps.** The “video while loading” title case and the “another queue remains named” guard already pass on the OP9-L2 snapshot, so neither can detect its respective fix (`W/__tests__/imageDialogTitle.test.ts:96-107`; `imageWidgetsUploadDialogGoes.test.ts:123`). Widget title tests stub the dialog and inspect its prop, not its rendered heading (`imageDialogTitle.test.ts:139-148,182-230`). The note and changelog call the queue page-owned, while `useUploadQueuesStore` is a shared Pinia store and the dialog key is a module-level ref (`dam/uploadQueue/store/uploadQueuesStore.ts:42`; `composables/useUploadQueueDialog.ts:4`); rows survive route changes.
