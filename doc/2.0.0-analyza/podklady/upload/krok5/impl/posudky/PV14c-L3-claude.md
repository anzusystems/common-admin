## Findings

### 1. Low — a refresh that names a configuration but finds no row of it still asks `default`'s DAM, and reports

`readTargetNow` takes the reader's queue from the first concerned row (`uploadSettlement.ts:644-647`); with none, `queueKey` is undefined and the library store's reader goes to `default` (`uploadQueuesStore.ts:140-143,149-155`), with `report: true`. Since L3 the target says which configuration it is for (`targetOf`, `uploadQueuesStore.ts:357-361`), but the read does not use it.

Scenario: `own`'s gallery, "save and apply" with two rows without their form: two refreshes wait on the chain (`UploadQueueDialog.vue:159-162`); the user closes the dialog (queue stopped and emptied) while the first is on the wire. The second runs with no row: `GET <default endPointAsset>/<own asset id>` on `default`'s DAM, its 403/5xx handed to the api error logger; with equal ids it may even answer. Nothing is written (no row is concerned), so it is a stray, reported request to the other DAM. The same request went out before L3 (without names), so not a regression, but it is a read across DAMs on a path the step scopes.

Fix: in `readTargetNow`, when `profile.configOf` and `target.configNames?.length` and no row is concerned, return `'settled'` without a read. Only for such a profile: admin-dam's read without a row still feeds `onAssetRead` (the open detail).

### 2. Low — several names on the immediate paths are read once, by one DAM, into the rows of all of them

Events with several names get one read per name (`uploadSettlement.ts:474-483`). `readTargetNow` (`refreshAsset`, `settleKnownProcessed`, `:639-681`) and `becomeOriginals` (`uploadSettle.ts:534-545`, used by `settleKnownDuplicate` and by the `duplicate` event, `uploadSettlement.ts:732-734`) read once, by the queue of the first concerned row, and write that answer into the rows of every named configuration. The note says so for the refresh (Rozhodnutia, last bullet), not for the duplicate; the types (`uploadSettlementTypes.ts:35-39,66-73`) and the changelog (`doc/changelog/2.0.0.md:75`, "an event that names several read once for each") promise per-configuration scoping without this exception.

Scenario: no library caller sends two names today (`targetOf` builds one). L4's `duplicate` event of a socket shared by two configurations will: the original read from one of them is written into the rows of both. Owner item 5 takes such two as one DAM, so that is accepted; but an application with its own queue and `configOf` that names two DAMs in `refreshAsset` or `settleKnownDuplicate` gets exactly the cross write the step removes.

Fix: split these two paths per name as `scheduleNamed` does (one read per configuration, by a queue of it), or say on `configNames` and `configOf` that on the refresh, the known processed and a duplicate several names are read once, by one of their queues (taken for one DAM).

### 3. Low — admin-dam's `notify()` now resolves two microtasks later

`scheduleNamed` returns `Promise.all(names.map(…scheduleRead…)).then(() => undefined)` (`uploadSettlement.ts:481-482`) also for a profile without `configOf`, where it used to return the waiter promise itself (snapshot `uploadSettlement.ts:447-467`). The writes are the same; the promise of `notify` for `processed`, `copied` and `metadata` resolves two microtask turns after the read's `releaseWaiters`, time in which the chain may start the next read (`:144-151`). The brief (line 22) asks that a profile without it settle "exactly as today"; admin-dam awaits these promises in its cases (`admin-dam/src/test/queue/slotNotifications.test.ts:144,161,175,193,…`) and its suite was not run. I found no case that would break; not verified.

Fix: `if (names.length === 1) return scheduleRead(assetId, fileId, intent, delayMs, names[0])`.

### 4. Low — the production entries of two scoped paths have no case: a dropped argument brings K2 back silently

The cases call the store (`store.queueItemDuplicate(ASSET, …, 'own')`; the brief's case reads "a widget under `own` picked a copy") and the list binding. The widgets' `queueItemDuplicate(…, damConfigName)` (`ImageWidgetInner.vue:551`, `ImageMediaWidgetInner.vue:569`, `ImageWidgetMultipleInner.vue:300`) and the dialog's "save and apply" refresh `{ queueKey: props.queueKey }` (`UploadQueueDialog.vue:160-162`) are pinned by nothing. `of` is optional and "left out: the rows of every queue" (`uploadQueuesStore.ts:68-72`), so losing the argument in a later edit compiles, keeps every case green, and writes `own`'s original into `default`'s rows again. By reading, all of them pass the right value today. The other uncovered places (`useUploadQueueItemRefresh`, the two `savingOf`) fall back to `default`, which matters only under a name and only skips a wait; lower risk.

Fix: one case per entry: a single widget under `own` whose copy to the licence answers `exists`, beside a `default` queue with a row of the same asset id (only `own`'s row becomes the original; `default`'s DAM gets no origin read); and "save and apply" of a dialog under `own` with a row without its form beside such a `default` row.

### 5. Low — documents: equal ids are not yet safe while notifications are on; the caches' second argument; one stale comment

- `doc/changelog/2.0.0.md:75` and `doc/guide/installation.md:65` conclude "so two configurations of two DAMs may give the same asset id" and add that a notification "still concerns the rows of every queue". With notifications on (admin-cms), a notification of `a-1` makes one read by the client of the first queue that has a row of it and writes it into the rows of every queue (`uploadSettlement.ts:553-560,613-622` with no names; `uploadQueuesStore.ts:245-265`): equal ids still cross on that path until L4. The sentence reads as if they were safe already.
- The types sentence of `:75` names the optional `queueKey` of the four cache functions, not that a profile with `configOf` gets it as a second argument: a `defineCached` `add` handed over as it is (as admin-dam's profile does, `admin-dam/src/domains/coreDam/asset/store/uploadQueuesStore.ts:270-275`; `defineCached.ts:122-146` takes every argument as ids) would cache the queue key as an author id. `uploadSettlementTypes.ts:103-108` says "given only to a profile with `configOf`", not the consequence.
- `uploadQueuesStore.ts:493`: "One answer for the rows of the asset in every queue" — now every queue of the configuration.

Fix: `:75` and `:65`: "… may give the same asset id; until a notification names its configuration (L4), it is read by the client of one queue and written into the rows of every queue". Types: "with `configOf` the four get the queue as a second argument (a `defineCached` `add`, which takes every argument as an id, is to be wrapped)". The comment: "in every queue of the configuration".

## Outside the step

### Medium — one read chain and one failure streak for every configuration of the store

`createUploadSettlement` keeps one `chain` (`uploadSettlement.ts:94,144-151`) and one `failing` (`:104,383-386,417-418,557,590`) for all queues. Both are per-DAM state that the plan's rule D1 keeps per configuration, and neither is in the plan's gap table.

Scenario: a page with `default` and `own` of two DAMs. `own`'s DAM is slow or unreachable: each of its poll reads holds the chain until it answers or the client times out (admin-cms: `envConfig.dam.apiTimeout`, `admin-cms/src/shared/apiClients/damClient.ts:13`), and every read of `default`'s DAM waits behind it: its poll, the reads notifications ask for, and the refresh the user presses (`uploadPoller.ts:78-88` awaits each read, so `own`'s queue always has one on the chain). While `own`'s failure streak runs (`failing = true` after its first reported failure), a failing read of `default` may report nothing (`report: !failing …`), so with both DAMs down only the first outage is written down until some read answers.

Fix: once every read is of one configuration (after L4), a chain and a `failing` per `configOf(queueKey)`, the unnamed reads of notifications until then on all chains or one of their own; `failing` per configuration can go now.
