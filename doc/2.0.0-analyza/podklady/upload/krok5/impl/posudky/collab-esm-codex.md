## Findings

1. **High — Socket.IO room lookups split during a rolling deploy.** The new pods use `channelPrefix: ${redisKeyPrefix}${streamName}` ([collaboration.ts](/home/volar/projects/petit/collaboration/src/server/collaboration.ts:37)); 7262b58 pods use the adapter’s default `socket.io` channel ([adapter.js](/home/volar/projects/petit/collaboration/node_modules/@socket.io/redis-streams-adapter/dist/adapter.js:68)). The adapter sends `fetchSockets()` requests and replies over those channels ([adapter.js](/home/volar/projects/petit/collaboration/node_modules/@socket.io/redis-streams-adapter/dist/adapter.js:123)). While old and new pods coexist, each sees only its own group’s sockets. If a user’s Socket.IO connection lands on an old pod and their Hocuspocus connection lands on a new one, document authentication finds no socket and rejects them ([authorizeDocument.ts](/home/volar/projects/petit/collaboration/src/server/document/authorizeDocument.ts:15)). Room occupancy and membership decisions can likewise omit users on the other group ([roomUserManager.ts](/home/volar/projects/petit/collaboration/src/manager/roomUserManager.ts:203)). The adapter-options test cannot detect this because it mocks `createAdapter` ([collaboration.test.ts](/home/volar/projects/petit/collaboration/test/collaboration.test.ts:14)).

2. **Medium — Sentry Issues lose the original error from normal application logging.** Call sites pass failures as metadata, for example the BullMQ worker’s `{ error }` ([queue.ts](/home/volar/projects/petit/collaboration/src/bullmq/queue.ts:35)). Winston moves that value into `metadata`, and the `printf` formatter deletes `metadata.error` before the Sentry transport receives the record ([appLogger.ts](/home/volar/projects/petit/collaboration/src/logger/appLogger.ts:50), [appLogger.ts](/home/volar/projects/petit/collaboration/src/logger/appLogger.ts:77)). The transport then constructs a new error from the log message ([sentryTransport.ts](/home/volar/projects/petit/collaboration/src/logger/sentryTransport.ts:45)). When a job fails, operators get a Sentry Issue saying “Job failed.” without the processor’s error type or original stack. The direct transport test supplies a top-level `Error`; the application logger test supplies only `jobId` ([sentryTransport.test.ts](/home/volar/projects/petit/collaboration/test/sentryTransport.test.ts:63), [logger.test.ts](/home/volar/projects/petit/collaboration/test/logger.test.ts:40)).

3. **Medium — The new integration test passes an impossible read-only socket state.** The test makes `fetchSockets(room)` return a viewer whose sole room is `${room}:info` ([hocuspocus.test.ts](/home/volar/projects/petit/collaboration/test/hocuspocus.test.ts:50)). Socket.IO’s `in(room).fetchSockets()` returns sockets *in that room* ([broadcast-operator.js](/home/volar/projects/petit/collaboration/node_modules/socket.io/dist/broadcast-operator.js:280)). Production authorization therefore never reaches its read-only branch for an info-only subscriber ([authorizeDocument.ts](/home/volar/projects/petit/collaboration/src/server/document/authorizeDocument.ts:16)). Such a viewer instead sees Hocuspocus authentication fail. The authorization logic predates this diff; the new test incorrectly claims that behavior works.
