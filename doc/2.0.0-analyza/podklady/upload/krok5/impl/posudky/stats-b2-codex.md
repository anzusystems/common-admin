**Verdict: B2 records participant edits and keeps the baseline out of room data, but I would not approve these commits against the stated reliability constraint.** Two verified ordering paths let stats work delay collaboration; one can let an older field value overwrite a newer one.

### High

- **A stats read can reorder a field release and lose another user’s value.** [releaseFieldLockListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/releaseFieldLockListener.ts:69) starts the baseline read, releases the lock at line 72, then awaits the read at line 87 before storing at line 91. If the room has no stored value and the stats Redis lookup stalls, another user can acquire the freed lock and write the field; the delayed release then stores the first user’s older value over it. The concurrent writer test uses a pre-stored value and does not cover this interval.

- **A first field write waits on stats I/O while holding the room lock.** [collabStatsEditManager.ts](/home/volar/projects/petit/collaboration/src/manager/collabStatsEditManager.ts:261) reads the baseline from the stats client when `HGET` finds no room value; [changeFieldDataListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/changeFieldDataListener.ts:46) awaits it inside the room action. That client has a 500 ms command timeout. A slow stats connection can therefore hold other room actions for up to that wait and can cause a lock lease failure. A failed read also silently omits the edit. This directly conflicts with “nothing on the hot path may wait on stats I/O.”

### Medium

- **The added baseline can prevent collaboration from starting, including with server stats disabled.** [articleCollabActions.ts](/home/volar/projects/petit/admin-cms/src/domains/cms/article/composables/articleCollabActions.ts:306) clones and sends the baseline on every `startCollab`; [articleEditCollab.ts](/home/volar/projects/petit/admin-cms/src/domains/cms/article/composables/articleEditCollab.ts:164) adds the body to that same acknowledgement. The collaboration server leaves Socket.IO’s 1,000,000 byte message limit at its default. An acknowledgement that fitted before B2 but exceeds that limit after the duplicate field values are added is rejected, so the second editor cannot join. `COLLAB_STATS_ENABLED=false` disables server counting, but does not stop this client work or payload.

- **`edited` does not literally mean “changed something.”** [collabStatsSessionHelper.ts](/home/volar/projects/petit/collaboration/src/util/helper/collabStatsSessionHelper.ts:269) requires three body edits, though one field edit suffices. If two participants each make one real body change, both retain `bodyEdits: 1` but have `edited: false`, and the session is classified `presenceOnly` at line 184. This follows the binding design’s `minEditOps: 3`; it conflicts with the owner’s stated priority for the per-participant answer.

- **A start without a baseline retains an earlier start’s baseline in the same session.** [collabStatsEditManager.ts](/home/volar/projects/petit/collaboration/src/manager/collabStatsEditManager.ts:245) returns when the moderator supplies no `collabStatsBase`; only the called [base Lua script](/home/volar/projects/petit/collaboration/src/storage/collabStatsRedis.ts:315) deletes the previous hash. If collaboration stops and starts again in the same stats session with an older client, a first write can be compared with the previous collaboration’s value and counted incorrectly.
