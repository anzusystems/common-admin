The committed tests cover two-pod counting, duplicate tabs, the 2-second timeout, caching, and 429 responses. I found no High issue, but the following Medium issues prevent an unconditional sign-off on correctness and performance.

- **Medium — A missing pod can produce a partial 200 response.** [collabStatsLiveManager.ts](/home/volar/projects/petit/collaboration/src/manager/collabStatsLiveManager.ts:78) trusts the adapter’s expected response count. The production Redis adapter derives that count from current pub/sub subscribers. If pod B loses its Redis subscription while its sockets remain connected, pod A expects no reply from B and returns its own counts as 200, potentially moving a shared article from `twoPlus` to `one`. The 2-second 503 path applies when B is counted as a subscriber but fails to answer.

- **Medium — Remote removal leaves `joinedAt` data behind.** [roomUserManager.ts](/home/volar/projects/petit/collaboration/src/manager/roomUserManager.ts:133) deletes the timestamp on a `RemoteSocket` snapshot, which does not update the socket’s data on its owning pod. [purgeRoomListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/purgeRoomListener.ts:41) bypasses that deletion altogether. A socket kicked from articles while remaining connected retains those timestamps; later room `fetchSockets()` calls carry the growing stale data. Live counts still use actual room membership, so I did not find a resulting miscount.

- **Medium — Each snapshot synchronously walks every socket on each answering pod.** [collabStatsRoomHelper.ts](/home/volar/projects/petit/collaboration/src/util/helper/collabStatsRoomHelper.ts:27) runs on the event loop for both local and remote snapshots. The 5-second single-flight cache limits snapshots per requesting pod, but the [remote handler](/home/volar/projects/petit/collaboration/src/server/collaboration.ts:53) has no such limit. With both pods polled and a large connected population, socket events wait while both scans run. The notes report measurements through 1,000 sockets; latency at larger scale is **not verified**.

- **Low — Part A reads future session keys that it cannot yet use.** [collabStatsLiveManager.ts](/home/volar/projects/petit/collaboration/src/manager/collabStatsLiveManager.ts:121) adds one session-key `GET` per listed room, up to 200 per bucket, although session state arrives in Part B1. That lookup and its second pipeline can be removed until B1.

The normal join, leave, and disconnect paths set or clear `joinedAt`; membership is deduplicated by user across tabs and pods, and the article filter excludes `:info` rooms.
