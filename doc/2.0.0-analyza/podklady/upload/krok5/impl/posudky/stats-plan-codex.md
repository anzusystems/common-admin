## Findings

This is a **design review**. At collaboration commit `d211edd`, the statistics endpoints, hooks, Lua scripts, and Mongo models are not present in `src`; findings about those components assess the proposed design, not a running implementation. §10 takes precedence over §9 below.

### High

1. **“Collaboration works fully when Mongo is down” is false for the current server.** §10.7 correctly notes the existing dependency, but §8 makes full operation a fixed requirement. Startup awaits the main Mongo connection in [index.ts](/home/volar/projects/petit/collaboration/src/index.ts:47), and body loading and saving use Mongo in [fetchDocument.ts](/home/volar/projects/petit/collaboration/src/server/document/fetchDocument.ts:33) and [storeDocument.ts](/home/volar/projects/petit/collaboration/src/server/document/storeDocument.ts:9). A separate statistics pool prevents *statistics* from blocking these calls; it cannot keep body collaboration working through a Mongo outage. Acceptance §10.13.5 tests only a two minute outage during an already running workload. State the narrower guarantee or redesign the existing body persistence path.

2. **Daily totals can be counted twice after a crash.** §10.4.4 and §10.5.2 propose Mongo `$inc` followed by a Redis `dailyDone` guard. If Mongo commits and the process dies before setting that guard, replay increments `collab_daily` and `collab_daily_users` again. The session `_id` prevents a duplicate session document, but does not make the daily increments idempotent; solo sessions have no Mongo session document at all. §10.13.6 tests a retry, but needs this specific commit/crash boundary. Use a durable per-session contribution marker committed atomically with the totals, or explicitly accept inaccurate totals.

3. **The body signal cannot establish “every edit exactly once.”** §10.1–§10.3 count `YjsUpdate` in `beforeSync` before application and classify `SyncStep2` solely as synchronization. The installed Hocuspocus code calls the hook before its switch and before `readUpdate` or `readSyncStep2` ([MessageReceiver.ts](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/server/src/MessageReceiver.ts:203), [MessageReceiver.ts](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/server/src/MessageReceiver.ts:233), [MessageReceiver.ts](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/server/src/MessageReceiver.ts:275)). A reconnect can deliver offline changes in `SyncStep2`, which the design itself acknowledges in §10.2; these are missed. A replayed or redundant `YjsUpdate` can be counted before Yjs determines whether it changes the document. The receiving pod’s Redis relay does **not** call this hook because it has no connection ([Redis.ts](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/extension-redis/src/Redis.ts:743)), so that particular double count is avoided.

4. **The proposed keyset indexes omit the tie breaker.** §10.5.1 indexes end at `startedAt`; §10.6.1 pages using `(sort key, _id)` and claims each deep page examines about 50 documents. None of the three compound list indexes includes `_id`. Sessions sharing a timestamp, duration, or active minute therefore lack an indexed total order for the proposed cursor. The `$in` `SORT_MERGE` and no-blocking-`SORT` claims are **not verified**. Add `_id` to each index and sort, then require representative `explain` results before relying on §10.13.2.

### Medium

5. **Field activity can be double attributed for one user action.** §10.2.1 counts a successful `changeFieldData`, then counts `releaseFieldLock` if its final value differs from the value at acquire. The same common-admin controls can emit both events—for example [AFormValueObjectOptionsSelect.vue](/home/volar/projects/anzusystems/common-admin/src/domains/form/components/AFormValueObjectOptionsSelect.vue:79) wires both methods; [collabField.ts](/home/volar/projects/anzusystems/common-admin/src/domains/collab/composables/collabField.ts:172) and [collabField.ts](/home/volar/projects/anzusystems/common-admin/src/domains/collab/composables/collabField.ts:224) send them separately. If a selection changes once and is then released, the proposed `changed` flag is true even though the release repeats the stored value. The server currently stores both paths ([changeFieldDataListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/changeFieldDataListener.ts:58), [releaseFieldLockListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/releaseFieldLockListener.ts:83)). Compare the release with the latest stored value, or define these as two messages rather than two edits.

6. **The per-socket write-order guard does not prove cross-socket field attribution.** §10.2.1 uses successful stores as edit signals. [fieldWriteOrder.ts](/home/volar/projects/petit/collaboration/src/util/helper/fieldWriteOrder.ts:9) orders only one socket’s room and field; a release runs outside the room lock and can store after the lock is released ([releaseFieldLockListener.ts](/home/volar/projects/petit/collaboration/src/server/event/listener/releaseFieldLockListener.ts:67)). A second user can acquire and change the field between those operations, after which the first user’s release may overwrite or be attributed as another edit. The guard does not serialize those users. Verify this race in B2 and tie release data to lock ownership/version.

7. **Active and idle time can become impossible values.** §10.1.4 sets `activeMs = active minute count × 60 s` and `idleMs = presentMs − activeMs`. A participant present for 10 seconds who makes one edit has 60 seconds active and −50 seconds idle. This affects the participant detail in §10.5.1 and §10.9. Cap active time to presence within each minute, or label it as an activity-minute measure rather than elapsed active/idle time.

8. **Rolling deployment can split a real session.** §9.1.3 acknowledges this, while §10.4 relies on the same membership source. The socket.io stream and cluster channel include the application version ([collaboration.ts](/home/volar/projects/petit/collaboration/src/server/collaboration.ts:38)); [roomUserManager.ts](/home/volar/projects/petit/collaboration/src/manager/roomUserManager.ts:214) obtains membership through `fetchSockets()`. During overlapping versions, an old pod cannot see a new pod’s members. Each can observe a first join or an empty room and produce a wrong peak or session boundary, despite the room lock. Keep the adapter communication namespace stable across compatible rolling versions, or mark the deployment interval as incomplete.

9. **The “small, bounded Mongo reads” argument omits document bytes and an unbounded daily document.** §10.5.1 caps session documents at 512 KB; §10.6.1 projects away `participants` only in the response. That projection does not make a noncovered list query read just the header; 50 large session documents can still require substantial Mongo I/O. §10.5.2 adds dynamic `byUser` and `byPair` maps to one `collab_daily_users` document per day, without a cap; the estimate of at most 1,000 pairs is not enforced. §10.13 measures documents examined and latency, but should also measure bytes read, daily document size and update contention at worst-case pair cardinality.

10. **B1 produces historical categories that B2 cannot repair from its planned data.** §10.12 orders B1 before edit capture in B2, while §10.1.6 defines `presenceOnly`, `separateEdits`, and `realCollab` from participant edits. B1 sessions finalized without edits cannot later be classified correctly. When C opens a 30-day tab, those records may look like “nobody edited.” Add a tracking-version or “edit data unavailable” category and exclude B1 records from edit-based rates; alternatively defer category finalization until B2.

11. **Part A’s room limit does not bound its cluster request.** §4.1 and §10.9 propose global `fetchSockets()` before limiting `live/rooms` to 200. That operation gathers all sockets, including their handshake data, across pods ([collaboration.ts](/home/volar/projects/petit/collaboration/src/server/collaboration.ts:37); the existing room-scoped use is [roomUserManager.ts](/home/volar/projects/petit/collaboration/src/manager/roomUserManager.ts:214)). Repeated Live and room-list polls can therefore cost work proportional to all connected sockets, even when the response is small. Before finishing A, share one cached snapshot between both endpoints, set a short cluster timeout and a request limit, and measure its size under the expected connection count. The planned core-cms super-admin check in §9.3 is sound; the public sys endpoint also remains directly callable by anyone holding the shared `SYS_API_TOKEN` (§4.2, §9.3).

### Low

12. **The Redis rate quoted is only the flush rate.** §10.10’s 30 rooms on two pods gives at most 60 active room-pod flushes per five seconds, or 12 flush round trips/s. For 90 editors each in a separate room, the figure is 18, rather than the table’s 36. Neither number includes membership Lua calls under the room lock (§10.4.1), or up to one additional `HGET` per release without the new client flag (§10.2.1). [FieldLockOptions](/home/volar/projects/petit/collaboration/src/types/ClientToServerEvents.ts:104) does not yet have `changed`. “No latency impact” remains **not verified**; the awaited membership Lua call necessarily adds a Redis round trip to joins and leaves.

13. **The 30-day summary and drill-down can disagree at the oldest boundary.** §10.5.1 expires sessions 30 days after `startedAt`, while §10.5.2 keeps daily summaries for 31 days to cover the first partial day. A 30-day tab can show that day’s count after its session documents have expired, leaving fewer drill-down rows than the displayed total. Align the retention windows or show that the first day’s detail is incomplete.

## Scope and next steps

The order **A → B1+B3 → B2 → C+E** is workable if B1 records are explicitly marked as lacking edit data. Move the Mongo outage test and the idempotent replay crash case into B1+B3’s acceptance gate; §10.13 currently makes the broad performance gate conditional on C. For A, prioritize the shared, bounded live snapshot and end-to-end super-admin authorization.

A smaller design could keep `collab_sessions` plus one `collab_daily` collection, with participant edit booleans and body/field counts, and omit per-minute arrays, pair rankings, and `collab_daily_users`. It would still answer who changed what in each multi-person session and support the requested tabs and drill-down; it would lose activity-time and “who with whom” rankings. Dropping the Redis outbox would simplify recovery further, at the explicit cost of missing statistics during Mongo outages while collaboration continues.

**Not verified:** Mongo execution plans (`SORT_MERGE`, covered reads, secondary routing), dotted-key behavior through the chosen Mongoose schema, actual Atlas tier/version, Lua races and BullMQ scheduling under failures, 512 KB BSON estimates, Sentry event rate, and the proposed latency/CPU thresholds. No installs, builds, tests, server starts, or writes were performed.
