## Timing and verification limits

A 1 s lease schedules extension about 500 ms before its drift-adjusted expiry ([exectionLockHelper.ts:10](/home/volar/projects/petit/collaboration/src/util/helper/exectionLockHelper.ts:10), [line 91](/home/volar/projects/petit/collaboration/src/util/helper/exectionLockHelper.ts:91)). The reported 45 ms loop maximum leaves substantial margin; its p99 does **not** establish a probability for longer pauses or slow Redis. A failed extension aborts the action: join and leave return `Failed`, while actions without acknowledgements log a failure. A 3 s lease with the *same* 500 ms threshold gives roughly the same stall margin per extension, but needs fewer extensions; a dead holder delays takeover by about 2 s more. The 20 s cap leaves no margin for four full 5 s waits, although the client’s default join acknowledgement expires at 5 s ([collabRoom.ts:52](/home/volar/projects/anzusystems/common-admin/src/domains/collab/composables/collabRoom.ts:52)).

With responsive Redis, an 8 s document cap normally precedes the earliest 9 s waiter give-up. If release is delayed, the last extended lease can outlive 8 s and a waiter can fail. During Redis outage, acquisition or release may remain pending: [redis.ts:12](/home/volar/projects/petit/collaboration/src/storage/redis.ts:12) sets `maxRetriesPerRequest: null`, and the cap timers start only **after** acquisition ([exectionLockHelper.ts:47](/home/volar/projects/petit/collaboration/src/util/helper/exectionLockHelper.ts:47)). Stored documents bypass that lock via [fetchDocument.ts:47](/home/volar/projects/petit/collaboration/src/server/document/fetchDocument.ts:47).
