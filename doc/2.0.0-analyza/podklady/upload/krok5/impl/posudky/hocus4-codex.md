## Findings

- **High — Hocuspocus 3 and 4 Redis extensions can leave documents divergent during a rolling deploy.** The server enables Redis with the same prefix across pods ([hocuspocus.ts](/home/volar/projects/petit/collaboration/src/server/hocuspocus.ts:23); [deployment](/home/volar/projects/petit/collaboration/docker/kubernetes/app-deployment.yaml:12)). Version 4 sends sync replies to a per-instance `#reply` channel ([installed v4 source](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/extension-redis/dist/hocuspocus-redis.cjs:57)); [v3.4.4 subscribes only to the document channel and sends replies there](https://github.com/ueberdosis/hocuspocus/blob/v3.4.4/packages/extension-redis/src/Redis.ts#L179-L198). If users edit the same document through old and new pods, an old pod cannot receive a v4 reply on that new channel. Their views can diverge, and whole-document Mongo replacements can persist one pod’s incomplete state ([storeDocument.ts](/home/volar/projects/petit/collaboration/src/server/document/storeDocument.ts:9)). The documented v3/v4 compatibility covers **provider-to-server WebSockets**, not this Redis extension exchange. [Hocuspocus release notes](https://github.com/ueberdosis/hocuspocus/releases/tag/v4.0.0).

- **High — Sentry’s active configuration permits the auth JWT cookie parts into telemetry.** `Sentry.init` leaves `dataCollection` at its v11 defaults ([index.ts](/home/volar/projects/petit/collaboration/src/index.ts:17)); cookies default to enabled ([installed defaults](/home/volar/projects/petit/collaboration/node_modules/@sentry/core/build/cjs/utils/data-collection/resolveDataCollectionOptions.js:3)). Authentication reconstructs the JWT from `anz_jp` and `anz_js` ([authorization.ts](/home/volar/projects/petit/collaboration/src/util/authorization.ts:16)). Neither name matches Sentry’s sensitive-name list ([installed filter](/home/volar/projects/petit/collaboration/node_modules/@sentry/core/build/cjs/utils/data-collection/filtering-snippets.js:4)); I ran that filter and both sample values remained intact. When an instrumented request carrying those cookies is captured, operators can see reconstructable token parts in Sentry. **Whether this exposure was introduced by the upgrade is not verified:** Sentry’s supplied migration guide says v11 defaults correspond to the prior `sendDefaultPii: true` setting.

- **Medium — the configured profile sample rate does not start profiling.** The app supplies `profileSessionSampleRate` and `nodeProfilingIntegration()` ([index.ts](/home/volar/projects/petit/collaboration/src/index.ts:23)), but v11 defaults `profileLifecycle` to `manual`; that branch does not start the profiler ([installed integration](/home/volar/projects/petit/collaboration/node_modules/@sentry/profiling-node/build/cjs/index.js:135)). No manual profiler start exists under `src`. With a nonzero configured rate, operators should therefore expect no CPU profiles. Whether profiling worked before this commit is **not verified**.

## Other checks and limits

The changed Hocuspocus hook fields match the installed v4 paths: database `fetch` receives load parameters, `store` receives the new payload, and `readOnly` is enforced for sync updates ([database extension](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/extension-database/dist/hocuspocus-database.cjs:50); [server](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/server/dist/hocuspocus-server.cjs:298)). `fetchDocument` runs before the document update listener is attached, so its initial Mongo write does not itself schedule a store ([server](/home/volar/projects/petit/collaboration/node_modules/@hocuspocus/server/dist/hocuspocus-server.cjs:1521)). The installed v11 default integrations still use the names `Redis` and `Mongoose`; the app’s filter matches them.

The provider leaves `sessionAwareness` off, and the [v4 release notes](https://github.com/ueberdosis/hocuspocus/releases/tag/v4.0.0) explicitly support either provider/server deploy order. The installed provider retains `WebSocketStatus`, `configuration.websocketProvider.status`, and `destroy()` ([provider source](/home/volar/projects/petit/admin-cms/node_modules/@hocuspocus/provider/dist/hocuspocus-provider.cjs:943)). I found no admin-cms source import of `@hocuspocus/transformer`.

**Not verified:** live Mongo/Redis/MySQL behavior, mixed-version Socket.IO adapter or BullMQ behavior, browser lifecycle behavior, and full article-schema preservation beyond the reported paragraph round trip.
