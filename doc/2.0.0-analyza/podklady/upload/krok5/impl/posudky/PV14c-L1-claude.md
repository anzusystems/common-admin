### 3. Low — the HMR rule "reload while a named store exists" holds only until the first accepted update

Where: `src/domains/dam/config/store/damConfigStore.ts:85,106-120`. Vite takes the callbacks of the version that registered them before it imports the new one (`node_modules/vite/dist/client/client.mjs:632-651`), and the new version's context clears them for the next update (`:479-481`). Importers (`damConfigState.ts:12`, the components) are not re-run: they keep calling the first version's `useDamConfigStoreOf`, whose `namedDefinitions` is the map they fill.

Scenario (by reading; `yarn playground:dev`, `package.json:46`): no named store yet; an edit of `damConfigStore.ts` runs v0's callback, which sees an empty map and hot-updates `default` (right). Fix: share the map across versions through `import.meta.hot.data` (`const namedDefinitions = import.meta.hot?.data.namedDamConfigDefinitions ?? new Map()`, and set it back on `hot.data`), or decide by the Pinia ids (`[...pinia._s.keys()].some((id) => id.startsWith('commonAdminDamConfigStore:'))` with `hot.data.pinia ?? getActivePinia()`). Correct the note.

## Outside the step

- An empty store for any name (noted by the implementer): the six components never check their name, so `configName="typo"` draws no icons or options silently, or throws "Custom form elements must be initialised." (`AssetCustomMetadataForm.vue:39-42`), where the widgets throw "Composable can't be used…". `AssetDistributionServiceNameFilter.vue:27-28` makes the store before `useCommonAdminCoreDamOptions` refuses the name (swap the two lines). Checking the name in the six components only when it is not `default` would not touch admins that configure no `coreDam`.
- Older, now per name: a store whose prv configuration was never loaded or filled has bounds 0..0 (`damConfigStore.ts:28-31`); `lastChunkSize` starts at 0 (`damUploadChunkSize.ts:16`), `returnFromRange` keeps it there (`:49-58`) and the loop `i += uploadedChunk.size` (`uploadService.ts:249-253`) sends empty chunks until the server refuses them (forever if it accepts). `addBy*` checks only the ext system (`uploadQueuesStore.ts:290-293,324-327`). Unreachable through the roots (they load the prv configuration before `ready`); reachable by an application that fills a named store's ext system but not its chunk bounds. A guard (refuse while `maxSize <= 0`) would close it.
- `useDamConfigStoreOf()` without a name is `default` everywhere, while `useDamConfigState()` without a name inherits in setup: as the brief defines them, but worth one sentence in the changelog for application authors.
