### M1. admin-dam: a type whose start-up read failed makes its metadata forms throw, and nothing in admin-dam reads it again

- Where: admin-dam `src/domains/system/composables/appInitialize.ts:119-124` reads the custom fields of the enabled types once, with the library's loader. `damConfigState.ts:183-193` resolves `true` when a type fails beside a type with fields, `:223-229` marks it, and `AssetCustomMetadataForm.vue:40-43` / `AssetCustomMetadataFormMassOperations.vue:44-47` now throw for it. admin-dam mounts them with no loader in front: `src/domains/coreDam/asset/components/AssetMetadata.vue:99-106` (`ADamAssetCustomMetadataForm`; list side panel `AssetListSidebarMetadata.vue:165-187`, drawn anew per asset, and detail `AssetDetailSidebarMetadata.vue:165`), `queue/AssetQueueItemEditable.vue:205-208` (`ADamUploadQueueItem` -> `UploadQueueItemEditable.vue:415-420`), `queue/AssetQueueSelectedSidebar.vue:28-30` (`ADamUploadQueueMassOperations` -> `AssetQueueSelectedSidebar.vue:288-351`, first type's panel opened at mount `:145-149`). `appInitialize.ts:124` is admin-dam's only call of the loader (grep); an ext-system switch reloads the page (`AssetToolbarExtSystemLicenceDialog.vue:164`). The note's "hostitelia ho pred tym nacitaju" does not hold for these hosts.
- Scenario: admin-dam starts over the `cms` ext system (all four types enabled, audio with custom fields: core-dam `config/packages/anzu_systems_core_dam_ext_systems.php:80-102, 264-265, 397-398`); the video read times out, image and audio answer. Start-up succeeds. Every video shown in the list side panel or the detail, every video row of the upload queue and the video panel of the mass operations throws "Custom form elements must be initialised." in setup. In production the form is not drawn (Vue 3.5.44 `runtime-core.cjs.prod.js:127-146`; Sentry's handler rethrows, `@sentry/vue/build/esm/errorhandler.js:27-31`, Vue logs it): the Metadata panel loses the custom fields and its whole slot with them (keywords, authors, single-use, TTS and internal switches, `AssetMetadata.vue:107-209`) until the page is reloaded, with no message. Before the step the panel lacked only the custom fields. For admin-dam, "as when the whole configuration is not loaded today" (brief) is its error page (`appInitialize.ts:125-131`), not a throwing form.
- Fix (owner's choice): in this repository, `loadDamConfigAssetCustomFormElements` given its own list of several types rejects when any of them fails (only admin-dam calls it so; the library's readers pass one type or none), and admin-dam goes to its error page as when the whole read fails; or in admin-dam, after `appInitialize.ts:124`, return `ERROR_PATH` when `getDamConfigAssetCustomFormElements(ext, type)` is `undefined` for an enabled type. Either way the changelog (`doc/changelog/2.0.0.md:256`, which says only "take it as a configuration not loaded") says that `ADamAssetCustomMetadataForm`, `ADamUploadQueueItem` and `ADamUploadQueueMassOperations` throw for such a type. Test: a start-up with one enabled type failing beside a type with fields ends on the error page (library variant: the loader rejects).

### M2. A failed read marks a type that another read has loaded: concurrent full reads of the widget roots

- Where: `damConfigState.ts:223-229` marks every type that failed now, also one the stored object holds loaded (`:209-221` keeps its fields in the new object).
- Scenario (admin-cms, article edit): the lead `AImageMediaWidget` (`ArticleEditForm.vue:148-155`) and the listing and social `AImageWidget` (`ArticleWidgetSupplementaryMedia.vue:42-51, 59-68`) share one upload licence and mount together; with no object for the ext system yet, each starts a full read of the four types (`AImageWidget.vue:120-130`). Root A's reads answer and it turns ready (`:137-138`). Root B's image read fails late (a timeout or 504 is the last to answer) while its audio read brings fields: its write keeps A's image fields and marks image not loaded. B shows "Loading Media Library config error" (`AImageWidget.vue:173-195`) over fields that are in the store; A stays ready, and the next upload into A draws `AssetCustomMetadataForm` in its sidebar (`UploadQueueDialogSingleSidebarMetadataContent.vue:90-94`), which throws: the upload dialog has no metadata inputs (fields, keywords, authors). Rows and mass operations of `AImageWidgetMultiple` the same (`UploadQueueItemEditable.vue:415-420`, re-created on `canEditMetadata`, `:417`). "Edit asset" or a picker's first opening heals it (they read `[image]`). Before the step this sequence ended with image loaded and every root drawn. Precondition beyond the bug's own (a read failing beside a type with fields): two roots reading at once, which every freshly loaded article page has, and the failing answer coming last.
- Fix: mark a failed type only when the stored object does not hold it loaded, e.g. in `:224-228` `...failedTypes.filter((type) => !storedConfig || customFormTypesNotLoaded.get(storedConfig)?.has(type))`. Test: two full reads in flight, the first answering image with fields, the second failing image beside audio with fields and answering last -> image loaded with the first's fields, both roots drawn (red now).
