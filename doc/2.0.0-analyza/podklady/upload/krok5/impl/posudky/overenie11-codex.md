## Claim 214 — the file-detail page keeps a deleted file’s address

**Verdict: PARTLY.** The stale address is reachable, including when the deleted file was **not** the main file. The claimed reload display is wrong: on a fresh load, the user is redirected to the app’s **not-found page**, rather than seeing an error on an empty asset detail.

## Claim 209 — per-case test memory growth

**Verdict: PARTLY.** Re-evaluation and at least one concrete retention path are proved; **80 MB per case, 3–4 GB per file, a 4 GB failure, and over 24 GB for the suite are not proved by code**.

**Mechanism.** Each case that calls [startUploadUi](/home/volar/projects/anzusystems/admin-dam/src/test/support/uploadUi.ts:83) resets Vitest’s evaluated modules (line 91), then dynamically imports common-admin, Vuetify components, i18n, app config, auth, and stores (lines 109–151); `mount` dynamically loads the requested component (lines 170–193). The example files call this helper and mount real views ([mainRouteChange.test.ts](/home/volar/projects/anzusystems/admin-dam/src/test/list/mainRouteChange.test.ts:145), [sidebarUnsaved.test.ts](/home/volar/projects/anzusystems/admin-dam/src/test/list/sidebarUnsaved.test.ts:71), [detailMainFile.test.ts](/home/volar/projects/anzusystems/admin-dam/src/test/list/detailMainFile.test.ts:195)). Inlined dependencies participate in that graph ([vitest.config.mts](/home/volar/projects/anzusystems/admin-dam/vitest.config.mts:52)). This does **not** execute `main.ts` or re-evaluate the test file’s existing top-level imports. Vitest’s reset clears cached exports, promises, and importers ([utils.DYj33du9.js](/home/volar/projects/anzusystems/admin-dam/node_modules/vitest/dist/chunks/utils.DYj33du9.js:27)); the registry alone does not prove that old exports remain held.

**Proved holder.** Each evaluation of common-admin’s module-level theme settings registers a media-query `change` listener with no removal path ([themeSettings.js](/home/volar/projects/anzusystems/admin-dam/node_modules/@anzusystems/common-admin/dist/domains/system/composables/themeSettings.js:11)). In happy-dom, registering it adds a `resize` listener to the shared window, whose closure retains that media-query object and callback ([MediaQueryList.js](/home/volar/projects/anzusystems/admin-dam/node_modules/happy-dom/lib/match-media/MediaQueryList.js:87)). Its module-level `useStorage` also registers a window storage listener ([themeSettings.js](/home/volar/projects/anzusystems/admin-dam/node_modules/@anzusystems/common-admin/dist/domains/system/composables/themeSettings.js:11), [VueUse index.js](/home/volar/projects/anzusystems/admin-dam/node_modules/@vueuse/core/dist/index.js:1919)). These prove retained listeners and associated state, **not** an 80 MB retained application per case. Module-level stores and singletons exist, but no independent old-case holder for them was established; nor was a persistent old app, mock-held server, or timer proved.

[stopUploadUi](/home/volar/projects/anzusystems/admin-dam/src/test/support/uploadUi.ts:208) unmounts its recorded apps, clears the body, restores timers and globals (lines 210–216). It does not remove listeners installed on `window` by the re-evaluated modules. The shared happy-dom window can therefore keep those listeners; clearing its body does not clear them.

**Smallest test-support fix: M.** Have `startUploadUi` record window/document listeners installed during its lifetime and have `stopUploadUi` remove any still registered after unmounting. This permits the proved listener-held evaluations to be collected while retaining per-case module isolation. Risk: listener tracking must account for removals already performed by components and must not remove runner-owned listeners; it needs a focused validation. It does not guarantee that every byte is released. Limiting `maxWorkers` bounds concurrent workers, **not growth within a large file**; Vitest’s default isolation is per **file**, not per case ([Vitest CLI](/home/volar/projects/anzusystems/admin-dam/node_modules/vitest/dist/chunks/cac.fSuRXrAx.js:849)). Splitting files or running smaller batches in separate workers would bound accumulation, at the cost of repeated startup and imports.

Read per-test `heapUsed` and the worker’s peak RSS; repeat after forced GC and inspect heap-snapshot retainer paths to distinguish retained objects from garbage awaiting collection.
