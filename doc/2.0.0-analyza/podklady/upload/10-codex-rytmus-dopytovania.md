1. **Use one coordinator per queue, with one in-flight read at a time.** Batch pending main-file asset IDs by licence, deduplicate IDs, and apply each result to its matching row. The backend accepts at most 50 IDs per request, but both existing frontend helpers split at 25, so the “one request per tick” estimate below requires changing that helper or using the endpoint directly ([backend limit](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/Controller/Api/Adm/V1/AssetController.php:139), [app helper](/home/volar/projects/anzusystems/admin-dam/src/domains/coreDam/asset/api/assetApi.ts:61), [library helper](/home/volar/projects/anzusystems/common-admin/src/domains/dam/api/damAssetApi.ts:29)). Batch reads return full asset details; measure their DB and response cost before rollout.

2. **Start each row’s clock when its finish request succeeds**, or when a copy/import returns an identifiable asset. Poll only rows awaiting file processing. Never poll rows still sending chunks. Give the queue its first scheduled read at the first offset below; a manual refresh, push event, or return to a visible tab may read sooner. Coalesce triggers arriving within 2 seconds and run one follow-up read if a trigger arrives during a request.

3. **Push off — dense schedule**, measured from the most recent row becoming eligible: reads at **+10, +25, +40, +55 seconds**; then every **30 seconds through 5 minutes**; every **60 seconds through 20 minutes**; then every **120 seconds**. The normal interval cap is **120 seconds**. Add stable queue-level jitter of up to ±10% to scheduled reads, without delaying manual refresh.

4. **Push on — backup schedule:** reads at **+30 and +60 seconds**; then every **60 seconds through 5 minutes**; every **180 seconds through 20 minutes**; then every **300 seconds**. The normal interval cap is **300 seconds**. A matching terminal push event settles that row immediately and removes it from status polling. A processed event may still need a separate, retried detail read to populate metadata.

5. **Reset only the queue’s cadence when a new row becomes eligible.** Its next read is 10 seconds away with push off, or 30 seconds with push on; existing rows retain their original ages and deadlines. A row settling, manual refresh, and tab visibility do **not** restart the dense phase. Manual refresh reads now, retains automatic polling, and cannot extend the row’s deadline. This prevents 50 rows settling one by one from keeping the queue permanently at its fastest rate.

6. **Use a soft horizon, followed by automatic long-tail checks.** For file type *t*, let \(D_t\) be its configured ack deadline in minutes—image **1**, document **2**, audio **5**, video **8⅓**—and let \(n\) be the largest locally known count of unfinished files of the same type and licence since this row finished. Set
   \[
   H_t=\min(240,\ \max(40,\ 20+nD_t))\text{ minutes}.
   \]
   Examples: **20 images: 40 min; 50 images: 70 min; one video: 40 min; 20 videos: about 187 min**. At \(H_t\), stop the normal schedule, show **“Taking longer than expected; checking occasionally”**, and continue an automatic check every **15 minutes while visible**. Keep **Refresh** and removal available; keep metadata disabled until `processed`. Do not label a timeout as server `failed`. This is “giving up” on frequent checks, not entering a manual-only mode.

7. **Treat that horizon as a user-facing threshold, not a backend guarantee.** Processing is serialized under a type-and-licence lock ([facade](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/Domain/AssetFile/AbstractAssetFileStatusFacade.php:205)). Pub/Sub uses **60/120/300/500-second** ack deadlines and redelivery backoff reaching **600 seconds** ([transport configuration](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/DependencyInjection/AnzuSystemsCoreDamExtension.php:167)); the handler rethrows and can retry `stored` work ([handler](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/Messenger/Handler/AssetFileChangeStateHandler.php:87)). No dead-letter limit was visible in the supplied configuration. **Assumption:** ack deadlines are useful sizing proxies, not maximum processing times; work from other editors sharing a licence is unknown to this browser. Those limits are why the 4-hour cap must lead to long-tail checks rather than a false failure.

8. **When hidden, suspend scheduled reads and retain wall-clock ages.** On becoming visible, make one immediate coalesced read, then resume at the interval appropriate to current age; never replay missed ticks. A row past its horizon enters the 15-minute long tail after that read. This avoids relying on throttled background timers while preserving automatic checks in an open, visible queue. A closed or cleared queue has no row to watch.

9. **Keep transport errors separate from file status.** For network errors and 5xx, leave rows pending, show a queue-level connection warning, and retry after **15, 30, 60, 120, then at most 300 seconds** with jitter; a successful read restores the normal schedule. On 401, attempt the app’s normal authentication recovery once, then resume after authentication; on 403, show an access error and retry at most every **5 minutes** and on an auth/visibility change. Do not mark files `failed`. A missing ID in a successful batch is a **per-row** problem: retry that ID once individually, then show “asset unavailable” with Refresh while continuing the other IDs. The repository filters by licence and IDs, so a nonexistent ID can simply be absent from the returned list ([repository](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/Repository/AssetRepository.php:82)). If a malformed ID rejects the whole batch, split it to isolate the offender.

10. **Make row application identity-safe and monotonic.** Capture queue generation, row object/key, asset ID, file ID, and upload attempt when issuing a read. Apply only if that exact row is still present, still awaiting this file, and the queue generation matches; clearing/removing invalidates the generation. Never let `uploaded`, `stored`, or `processing` overwrite a terminal result or re-enable metadata. One queue request in flight plus a coalesced follow-up prevents older reads overtaking newer reads. A row finishing during a request joins the follow-up, not the old response. A push event and read may arrive in either order: settle a matching terminal event immediately, ignore a later stale nonterminal result, and use a fresh read to resolve conflicting terminal evidence. If a push-triggered read precedes DB visibility, retry after **2 then 5 seconds**; a nonterminal read is never grounds for failure. Backend processing commits before its changed-file event is dispatched ([facade](/home/volar/projects/petit/core-dam/vendor/anzusystems/core-dam-bundle/src/Domain/AssetFile/AbstractAssetFileStatusFacade.php:299)).

11. **Qualify the batch architecture for slot files.** App slot rows can share an asset but have distinct file IDs, while the asset detail’s `mainFile` describes only one file; today’s fallback explicitly refuses to infer a slot’s status from another main file ([app fallback](/home/volar/projects/anzusystems/admin-dam/src/domains/coreDam/asset/api/fileApi.ts:148), [row matching](/home/volar/projects/anzusystems/admin-dam/src/domains/coreDam/asset/store/uploadQueuesStore.ts:488)). Use a file-specific read for slots, or add a backend batch file-status endpoint. Do not settle every row sharing an asset ID from one asset-detail result. **Assumption:** the existing file-specific endpoints return the slot status needed here; their response contract was not verified for this design.

12. **Load estimate, assuming all 600 rows remain pending, one licence per queue, one 20-ID request per tick, and visible tabs:** 30 editors × one queue each yields **120 requests/min** in the dense first minute, **60/min** from 1–5 minutes, **30/min** from 5–20 minutes, then **15/min**. Sparse mode yields **60, 30, 10, then 6 requests/min** over those periods. Today’s per-row schedule produces **600-request bursts** at +10, +50, +140, and +300 seconds: **2,400 requests in 5 minutes**, versus **360 dense** or **180 sparse**. The dense 5-minute run can nevertheless return up to **7,200 full asset DTOs**, versus today’s **2,400 single-asset reads**; settlement should reduce that figure.
